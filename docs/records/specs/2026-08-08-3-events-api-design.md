# イベント取得API 設計書

- 対応 Issue: [#3 openapi.yaml とイベント取得API](https://github.com/TakuyaAsaoka/ichikabu/issues/3)
- 根拠: [全体設計書](2026-08-02-1-ichikabu-design.md)（§4 データモデル・§5 表示ルール・§7 技術選定・§8 `openapi.yaml` とのズレの検知・§9 認証・§14 未決事項 #4）

## 1. 結論

**`GET /api/events` の1本だけを作る。クエリパラメータなし。認証ユーザーの保有に対応するイベントを全件、`Event` の配列で返す。** これが全体設計書 §14 未決事項 #4（APIのエンドポイント設計）の決着である。

| 項目 | 決定 |
|---|---|
| エンドポイント | `GET /api/events` の1本のみ。パラメータなし |
| 認証 | Bearer（§9）。認証なしは 401、本文なし |
| レスポンス | `Event` の配列そのもの。ラッパーなし |
| 実装 | `server/app/api/events/route.ts` の1ファイル |
| スコープ外 | write 系API・権利確定日/配当落ち日（Issue #10）・月の絞り込み（iOS側の責任） |

## 2. エンドポイント（未決事項 #4 の決着）

| 判断 | 根拠 | 却下した案 |
|---|---|---|
| 全件返却の1本。期間・月の絞り込みパラメータを持たない | 全体設計書 §7「iOSはローカルDBを持たず、データは数KB。起動時に1リクエストで全部取れる」。月をスワイプしても通信もローディングも発生しない。人力登録のデータ量は年に数十KBで収まるため、絞り込みの複雑さを買う理由がない。転送量が問題になったら期間パラメータを後から足せる | `?from=&to=` の期間指定／`?month=YYYY-MM` の月指定。どちらも月をスワイプするたびに通信が要り、先読みとキャッシュの設計がiOS側に発生する |
| 認証なしは 401 を本文なしで返す | §7「401が返ったら再ログイン画面に落とす」ので本文は使われない | エラー本文の定義 |

**帰結**: 全体設計書 §5 の「月の絞り込みは重なり判定で行う」（`start_date ≦ 月末 AND COALESCE(end_date, start_date) ≧ 月初`）はサーバーには実装しない。iOS側の表示処理の責任になる。

## 3. レスポンスの Event 型

`Event` の配列をそのまま返す（`{ events: [...] }` のようなラッパーは作らない）。

| フィールド | 型 | 備考 |
|---|---|---|
| id | integer | |
| kind | `"market"` \| `"theme"` \| `"stock"` | 種別（→ §4） |
| title | string | シートの見出し |
| shortLabel | string | セルの略号 |
| startDate | date | |
| endDate | date \| null | null は単日 |
| time | string \| null | JST |
| importance | integer（1〜3） | |
| note | string \| null | シートの補足 |

| 判断 | 根拠 | 却下した案 |
|---|---|---|
| 全フィールドを `required` にし、値が無いものは `null` を入れる | オプショナルにすると Swift 側で二重オプショナルになる | nullable フィールドをオプショナルで表す |
| `importance` は `minimum: 1` / `maximum: 3` で表す | `enum` にすると openapi-typescript の生成型が `1 \| 2 \| 3` になり、DBの `smallint`（TypeScript では `number`）を代入できず、意味のないキャストが要る | `enum: [1, 2, 3]` |
| `source_url` は契約に載せない | 「どこで日付を確認したか」という運用者向けの記録（§4.2）で、§10 のiOS画面に出す要件がない。必要になったら1行足せる | 契約に含める |
| ~~対象の識別子（`market` / `theme_id` / `stock_id` の生の値）や対象の名前（銘柄名・テーマ名）は返さない~~ **→ Issue #86 で識別子を返す形に変えた**（[ログイン廃止 設計書](2026-08-14-86-no-login-design.md) §3.1）。当時の根拠は「iOS がこれを使う用途は §10.2 の色分けだけ」だったが、iOS が自分で絞り込むようになり、対象の識別子が要る用途ができた。名前は今も返さない | iOS がこれを使う用途は §10.2「色は種別だけ」（銘柄＝琥珀・市場＝藍・テーマ＝紫）だけで、`kind` で足りる。銘柄名はもともと人が `title` に書く | 対象の情報を含める |

## 4. kind の導出

DBの `event` は CHECK 制約 `num_nonnulls(market, theme_id, stock_id) = 1` により「ちょうど1つだけ非NULL」が保証されている。埋まっている列を見て `kind` を決める。

| 判断 | 根拠 | 却下した案 |
|---|---|---|
| TypeScript 側で、早期 return の小さな関数として導出する（三項演算子を入れ子にしない） | SQL の `CASE` 式に寄せると Drizzle の型注釈を自分で付ける手間が増える | SQL の `CASE` 式 |
| ~~最後の `stock` は else 扱いにする~~ **→ Issue #86 で明示の分岐に変えた**。`target` は分岐の中で `stock_id` の**値そのもの**を使うため、else では取れない（型が `number \| null`）。**「例外は投げない」のほうは変えていない**。3列とも埋まっていない行は `null` を返し、呼び出し側が落とす | CHECK 制約は TypeScript の型からは見えないため、型の上では「3列とも null」の可能性が残るが、DBが弾いているので例外は過剰 | 「3列とも null」で例外を投げる |

## 5. 表示対象の判定（§5）

1本のクエリの OR で書く。

```sql
WHERE e.market = 'GLOBAL'                        -- 全員に出る
   OR e.market IN (保有銘柄の市場)                 -- JP保有者にJP、US保有者にUS
   OR e.stock_id IN (保有している銘柄)
   OR e.theme_id IN (保有銘柄が所属するテーマ)
ORDER BY e.start_date, e.time, e.id
```

- `market` が NULL の行（テーマイベント・銘柄イベント）は `NULL IN (...)` が真にならないため、市場の2条件に引っかからない。CHECK 制約の排他がそのまま効く
- US市場のイベントが JP保有者に返らない理由: 判定は「イベントの市場」と「保有銘柄の市場」の一致で決まる（§5）。日本株にも効く米国の出来事（FOMC・米CPI・米雇用統計）は `US` ではなく `GLOBAL` で登録する決まり（§4.2）なので、`US` に残るのは US株保有者にしか関係しない出来事だけになる。この判定の正しさは登録時に `GLOBAL` と `US` を正しく選べるかにかかっており、そこは管理UI（Issue #7）側の運用の責任
- `stock.market` は `JP`/`US`、`event.market` は `JP`/`US`/`GLOBAL` だが、どちらも `text` + CHECK なので比較できる（§4.2 で PostgreSQL の列挙型を却下した理由そのもの）

## 6. 実装の置き場所

| 判断 | 根拠 | 却下した案 |
|---|---|---|
| `server/app/api/events/route.ts` の1ファイル。クエリを別モジュールに切り出さない | 呼び出し元がここしか無く、テストはハンドラ越しに書けば認証と判定を同時に固定できる | クエリの別モジュール化 |
| `next/headers` は使わず `request.headers` を読む | vitest からハンドラを直接呼べる形を保つ。既存の `app/api/health/route.ts` のテストと同じ流儀 | `next/headers` |
| レスポンスの組み立ては `openapi-typescript` の生成型（`src/generated/api.d.ts` の `components["schemas"]["Event"]`）に縛る | §8「server実装だけ変えて `openapi.yaml` を忘れた → tsc が落ちる」がこれで成立する | 型に縛らない実装 |

## 7. テスト

`server/app/api/events/route.test.ts`。利用者を2人 seed し、それぞれのトークンで叩いて返る集合を比べる。テストケース名は日本語。

| ケース | 固定する内容 |
|---|---|
| Bearer なし | 401 |
| 市場イベント | JP保有者に JP と GLOBAL が返り、US は返らない |
| テーマイベント | テーマ所属銘柄の保有者にだけ返る |
| 銘柄イベント | その銘柄の保有者にだけ返る |

契約テスト（`openapi.yaml` とレスポンスの実際の値の突き合わせ）は入れない。§8 で却下済み。

## 8. スコープ外

| 項目 | 理由 |
|---|---|
| write 系（登録）のAPI | 管理UIは Next.js 内で完結するため、iOS が読む read 系だけを契約に載せる |
| 権利確定日・配当落ち日（Issue #10） | `event` の行にならず計算で出すため `id` も持たない。DBから取ったイベントと計算で出したイベントを同じ配列に混ぜるときに `Event` 型の見直しが要るが、それは Issue #10 で決める。今回の契約はDBの行だけを表す |
| 月の絞り込み | iOS側の表示処理の責任（→ §2） |
