# 開発用と実機での常用をまかなう配信先（Issue #74）

iOS アプリの接続先が `http://localhost:3000` に固定されていて、実機では届かない。実機で毎日使える場所に Next.js を置く。

**本番の選定ではない。** Issue #16（ホスティングとDBのプラットフォーム選定）は保留のまま。あちらは収益化を前提とした本番の選定で、判断材料（想定規模・利用頻度）が未確定である。**このIssueはその判断材料を取るための足場。** #16 自身が開発用DBについて「本番の選定を待つ必要はない。開発用に1つ選び、本番選定時に `pg_dump` で移せばよい」と書いた切り分けを、置き場所にも当てはめる。

## 1. 選んだもの

| | 選んだもの | 理由 |
|---|---|---|
| アプリ | **Netlify の無料プラン** | Vercel は Hobby が非商用限定（規約の例に**広告の掲載**が挙がっている）。Render は15分でスリープし、1日1回開くアプリと相性が悪い。この2つを外すと、残る無料は Netlify だけ |
| DB | **Supabase の無料プラン（東京）** | 東京リージョンがある。7日間さわらないと停止するが、毎日使うため止まらない |

DBをアプリと別のサービスに置くのは、置き場所を替えてもDBを引っ越さずに済むため。

### 棄却した道

| 案 | 棄却の理由 |
|---|---|
| Mac の LAN IP を直接指す | 家の中でしか使えず、利用頻度の実測にならない。暗号化なし通信の許可をアプリに入れることにもなる |
| トンネルで Mac を公開 | Mac を起動しっぱなしにする必要があり、開発用DBが外から届く |
| Fly.io / Railway | 月$2〜5かかる。無料で始めて足りなければ移る |

## 2. デプロイは自動にしない

無料プランは**月300クレジット**で、デプロイ1回が**15クレジット**、転送が**1GBあたり20クレジット**。

```
300 ÷ 15 = 月20回。転送に回すぶんを引くと実際は15回前後
```

自動デプロイにすると、マージのたびに15クレジット減って月20回で尽きる。**枠を使い切るとサイトが停止する**（URLに `Site not available` が出る）。実機で毎日開くアプリが落ちるということなので、まとめて手で実行する（`netlify.toml` に理由を書いた）。

## 3. 決めたこと

Issue #74 の「残る判断」5件の結論。

| # | 判断 | 結論 | 理由 |
|---|---|---|---|
| 1 | マイグレーションの流し方 | **手元から手で流す。ビルドに混ぜない** | 混ぜると壊れたマイグレーションでサイトごと落ちる。直すのにもう15クレジット要る。接続文字列も用途で分かれる（実行時は transaction pooler、流し込みは direct connection） |
| 2 | iOS の接続先の切り替え | **シミュレータは手元、実機は配信先**（`#if targetEnvironment(simulator)`） | ビルド構成（Debug/Release）で分けると、Xcode から実機へ入れたとき Debug になり手元を見てしまう。実機は Mac と別の機械なので `localhost` はどのみち届かない |
| 3 | サイトの数 | **1つ。常用DBだけを見る** | 2つ立てるとデプロイのクレジットも2倍。開発中の確認は手元の `next dev` で足りる |
| 4 | 利用者の投入 | 手元から `DATABASE_URL` を配信先に向けて `pnpm db:seed` を1回 | 利用者は1人で、既にその形になっている（全体設計書 §9）。**確認用の銘柄・保有・イベントも一緒に入る**（`src/db/seed-event.ts`）。要らなければ管理UIから消す |
| 5 | クレジット残量の見方 | Netlify の画面（Team → Usage）。デプロイ前に見る | 枠切れでサイトが止まるため、気づける場所を手順書に書く |

判断2の引き換え: **実機から手元の開発サーバーは見られない。** 同じ Wi-Fi に限られるうえ、暗号化なしの通信を許す設定をアプリに入れることになるため用意しない。

判断3の引き換え: **配信先で試すことは、常用しているデータの上で行うことになる。** 壊すとカレンダーが壊れる。Supabase の2つ目のプロジェクトは本番選定まで使わない。

## 4. 置いたもの

| ファイル | 中身 |
|---|---|
| `netlify.toml` | ビルドの起点を `server/` にする。`pnpm gen` が `../openapi.yaml` を読むが、手元でビルドして配信するためリポジトリ全体があり解決できる。Node は22で固定（`engines` は `>=20.12`。向こうの既定に任せると、既定が変わった日に結果が変わる）。**配信物の置き場所は書かない**。Next.js は設定不要で、アダプタが決めるため |
| `docs/guides/deploy.md` | デプロイ・マイグレーション・利用者投入・クレジットの見方・環境変数 |
| `ios/Ichikabu/APIClient.swift` | 接続先を実行環境で分ける。配信先のURLは `deployedBaseURL` の1箇所 |

配信先の秘密（`DATABASE_URL`・`BETTER_AUTH_SECRET`）は Netlify の環境変数に入れ、リポジトリには入れない。**`BETTER_AUTH_SECRET` は手元と別の値にする。** 共有すると、手元で作ったトークンが配信先でも通る。

## 5. 確かめていないこと

**この設計はまだ配信先で動かしていない。** アカウントが要るため。次の3つは実際に上げてから確かめる。

1. **Netlify が Next.js 16 をビルドできるか。** 公式は「13.5以降のすべてのバージョンを支え続けている」と書いているが、16 を名指しした記述は無い
2. **手元でビルドした成果物に `server/.env.local` の値が混ざらないか。** 手元ビルドを選んだため、配信先の環境変数より手元の値が勝つ余地がある。最初のデプロイのあと、配信先が Supabase を見ていることを1回確かめる
3. **Better Auth が配信先のURLでサインインを通すか。** `BETTER_AUTH_URL` を入れればそのオリジンが信頼される作りになっていることはコードで確認済み（`better-auth` の `context/helpers`）だが、実際に通したわけではない
