# イチカブ 設計書

## 1. 概要

自分の持ち株を登録すると、関連するイベント（決算・経済指標・テーマ関連イベント）がカレンダーで見えるiOSアプリ。イベントは運用者がWeb管理UIから人力で登録する。

| 項目 | 値 |
|---|---|
| アプリ名 | **イチカブ** |
| サブタイトル | **一日一株。持ち株の決算・イベントカレンダー**（21文字／App Store枠は30文字） |
| 由来 | 「一日一善」のもじりで「一日一株」。**朝1回ざっと見る**という利用シーンを名前にした。略した「イチカブ」だけでは由来が伝わらないが、サブタイトルと並べて読むことで成立する |
| マスコット | **ケッサンショウオ**（→ §10.4）。アプリ名とは意図的に切り離してある |
| リポジトリ名 | `ichikabu` |

**名前を機能に縛らなかった理由**: カレンダーはMVPであり、将来はポートフォリオ分析へ広がる（→ §14「将来スコープとの矛盾」）。「カブレンダー」「カブイベ」のような機能名を含む候補は、この理由で却下した。「一日一株」は機能ではなく**利用の習慣**を指すため、機能が増えても破綻しない。

**価値の中心**: 決算日・権利確定日は証券会社アプリに既にあり差がつかない。「このテーマのこのイベントでこの銘柄が動く」という紐付けは自動取得できず、どこにも売っていない。**人力の管理UIはつなぎではなく製品の中身である。**

- 利用者: 当面は自分1人。将来App Store配信を想定
- 対象: 日本株中心、米国株も視野

**本文書の記述には、確定度の異なる3種類が混在している。** 読むときは必ず区別すること。

| 分類 | 意味 |
|---|---|
| **A. 決定事項** | 明示的に決めたもの |
| **B. 技術的に導かれたもの** | A から論理的に導かれ、**前提が変わっても妥当性が残る**もの |
| **C. 仮定に依存するもの** | **未確定の前提の上に載っている**もの。前提が動けば覆る |

収益化の形（広告か課金か）はこの一覧から外れた。**広告で始めると決めたため**（→ §14 #3）。実測を待たずに決めたのは、実測が動かすのが広告側の数字だけで、結論の向きを変えないと分かったからである。

## 2. スコープ

| やること | やらないこと |
|---|---|
| 持ち株を選ぶ（iOSアプリの中。端末に保存する） | 株価・損益・チャートの表示 |
| イベントの人力登録（Web管理UI）と、配信されている公表予定の取り込み（`pnpm import:stat` → §2.1） | **HTML を読み解いて日付を取り出すこと**（＝スクレイピング → §2.1） |
| イベントのカレンダー表示（iOS） | 複数ユーザー対応・サインアップ |
| テーマによる銘柄とイベントの紐付け | プッシュ通知・ウィジェット（→ §12） |

### 2.1 公表予定の取り込みについての判断

**配信されている構造化データ（XML・ICS 等、機械が読む前提で形が決まっているファイル）を読むのは可。HTML を読み解いて日付を取り出すのはやらない。これは初回リリースだけの話ではなく、この先も変えない。**

配信されている公表予定を読んでよいのは、次の4つをすべて満たすときだけである。

1. 発信者が公表予定を**構造化データとして配信している**（XML・ICS・CSV・JSON 等）
2. その取得を発信者が**禁じていない**（robots.txt と利用条件を読んで確かめる）
3. §5.1 の表で「使う」になっている出典である
4. 条件が `event.source_name` と `event.source_url` **だけで満たせる**。事前の連絡・加工したことの明示など、手続きの要る出典は対象外にする

**4つとも、満たさなければやらないという形で読む。** 特に4は「出典の名前とURLを出せば済むか」を問うている。日銀は商用で使うなら事前の相談を求めており（§5.1）、2列を埋めるだけでは満たせない。

**公表予定の日付を登録するのは転記であって、編集・加工ではない。** 公共データ利用規約 1.1 は編集・加工して使う場合に「加工したこととその主体」の記載も求めているが、日付をそのまま写すだけならこれに当たらない。**この一点をもって、公共データ利用規約を採用している出典は条件4を満たす。**

総務省統計局については、さらに強い記述がある。統計局のページは数値データと単純な表がそもそも著作権の対象外で規約の適用が無いと書いている（→ [出典の利用条件](../../reference/source-terms.md)）。ただしこれは統計局の自前のページにしか無く、デジタル庁の規約の条文には無い。**内閣府・財務省に同じことは言えない。**

**やらないこと**は2つに絞られる。

| やらないこと | 理由 |
|---|---|
| HTML を読み解いて日付を取り出す（スクレイピング） | ページの作りが変わると壊れる。発信者が想定していない読み方になる |
| 取得を禁じている出典から取る | 条件2に反する |

出典ごとの当てはめ。**何を見てそう判断したか（配信の形・掲載期間・`robots.txt` の中身・条文の引用）は [出典の利用条件](../../reference/source-terms.md) にある。** ここに置くのは判断と、その一行ぶんの理由だけ。確認日は突き合わせに要るので両方に書く。

| 出典 | 判断 | 理由 |
|---|---|---|
| 総務省統計局 | **読んでよい** | 4条件をすべて満たす（確認日 2026-08-12） |
| 内閣府 ESRI（GDP速報） | やらない | 条件1を満たさない。HTML の表のみ（確認日 2026-08-12） |
| 財務省貿易統計 | やらない | 同上（確認日 2026-08-12） |
| FRB（FOMC日程） | やらない | 同上（確認日 2026-08-11） |
| BLS（米CPI・雇用統計） | やらない | 条件2を満たさない。ICS を配信しているが取得を禁じている（確認日 2026-08-11） |
| 各社のIRページ（決算発表予定） | **確かめていない** | 会社ごとにページが違い、まとめて調べていない。使いたくなった会社があれば、そのときに1社ずつ確かめる |

**手で登録する経路は無くならない。** 読んでよいと決まったのは今のところ総務省統計局だけで、件数の一番多い決算発表日は引き続き人が入れる。管理UIの貼り付けによる一括登録（→ [Issue #60](https://github.com/TakuyaAsaoka/ichikabu/issues/60)）がその手段になる。

**読んでよいと決めた後、実装まで進んだ。** 消費者物価指数の公表予定を `pnpm import:stat` で登録できる（→ [統計局の取り込み 設計書](2026-08-12-64-import-stat-schedule-design.md)）。**取り込むのは統計局が配信する10本のうちこの1本だけと決めており、他の9本は使いたくなったときに1本ずつ中身を確かめる**（同 §1 #4）。**統計局の取り込みで未決なのは、取りに行く間隔だけである。** いまは月1回を目安に手で実行しており、決まった間隔での自動実行は作っていない（→ [Issue #107](https://github.com/TakuyaAsaoka/ichikabu/issues/107)）。4条件は可否を決めるだけで、取りに行く間隔は決めていない。BLS が取得を禁じる理由として挙げている「遅延を起こし、他の利用者が必要なときに情報を得るのを妨げうる」（`source-terms.md`）は、禁じていない出典にも同じく当てはまる。**間隔を決めるときはこの一文が効く。**

**この判断は §5.1 と矛盾しない。** §5.1 は「安全性は方式ではなく出典の選び方によって担保される」と書いている。取得を自動にしても出典の選び方は変わらない。§5.1 の表が「どの出典を使ってよいか」を決め、この節が「どう取ってよいか」を決める。

一律でやらないと決めていたところから条件で分ける形に変えた経緯は、§14 #14 にある。

## 4. データモデル（PostgreSQL）

### 4.1 テーブル一覧

| テーブル | 主な属性 | 制約 |
|---|---|---|
| `user` | 利用者 | **Better Auth が生成するテーブルをそのまま使う**（→ §9）。当面1件を手動投入 |
| `stock` | `market`(JP/US)・`ticker`(文字列)・`name`・`fiscal_month`(決算月、JPのみ) | PKはサロゲートID。UNIQUE(market, ticker)。`fiscal_month` は1〜12かつJP銘柄のみ（CHECKで強制。US銘柄に入るとJPの休場日カレンダーで計算した権利確定日が出てしまうため。→ §14 #8）。`ticker` は `^[0-9A-Z.-]+$`（全角混入の防止） |
| `theme` | 名前 | 名前UNIQUE |
| `theme_stock` | theme × stock | PKは (theme_id, stock_id) の複合 |
| `event` | `title`・`short_label`・`start_date`・`end_date`(NULL=単日)・`time`(NULL可)・`importance`(1〜3)・`note`(NULL可)・`source_url`(NULL可) ＋ **対象の3列** `market`(JP/US/GLOBAL)・`theme_id`・`stock_id` | 日付・時刻はすべてJST。対象の3列は**ちょうど1つだけ非NULL**（CHECK）。`end_date` は `start_date` より後 |
| `audit_log` | `user_id`(NULL=人以外)・`action`(create/update/delete)・`resource_type`・`resource_id`・`previous_values`(jsonb)・`new_values`(jsonb) | 誰がいつ何を作成・更新・削除したかの記録（→ [監査ログ 設計書 §5](2026-08-14-82-multi-editor-audit-design.md)）。索引3本（`created_at`・`user_id`・`(resource_type, resource_id, created_at)`）。IPアドレスとブラウザの種類は持たない |

**全テーブルに `created_at` を持つ**（DBのデフォルト値で自動設定。アプリコードは書かない）。

**イベントは日単位で確定した日付のみ登録する。** 月・旬単位でしか公表されていない予定（「5月 期末決算発表」等）は、日付が確定してから登録する。仮の日付を入れてはならない（→ §4.2「日付は3列」）。

外部キーの削除時の挙動:

| 外部キー | 指定 | 理由 |
|---|---|---|
| `theme_stock` の2つ | CASCADE | 純粋な対応表。テーマ削除は通常の整理作業 |
| `event.theme_id`・`event.stock_id` | RESTRICT | イベントは人力登録した製品の中身（→ §1）。親の削除で黙って消してはならない。SET NULL は対象の3列が全てNULLになりCHECK違反を招くため不可 |
| `audit_log.user_id` | RESTRICT | **監査ログは過去の事実の記録で、他のテーブルへの DELETE で書き換わってはならない。** SET NULL にすると、入力者を1人消した瞬間にその人の記録が「人以外がやった」と読める行に化ける（取り込みスクリプトに DELETE は無いのに「取り込みが削除した」が集計に出る）。`seedUser` は `crypto.randomUUID()` で採番するため、同じメールアドレスで入れ直しても紐づけは戻せない。入力者をやめさせるのに `user` の行を消す必要は無く、メールアドレスを書き換えればパスワードでも Google でもサインインできなくなる（Google の初回サインインは §9 のフックが拒む） |

休場日はテーブルにしない。年1回更新すれば足りるリストにDBは過剰であり、アプリ内静的定数で持つ。

### 4.2 設計判断と根拠

| 判断 | 根拠 | 却下した案 |
|---|---|---|
| `ticker` は文字列 | 日本の証券コードは2024年から英字入りが実在（`130A` 等）。数値型は破綻している | 数値型 |
| PKはサロゲートID（`stock`・`theme`・`event`）<br>※サロゲートID＝業務上の意味を持たない、DBが振るだけの連番のID | ティッカー変更・社名変更が列の書き換えだけで済み、`event`・`theme_stock` の参照が無傷。ただし `theme_stock` は**参照される側にならない**ため複合PKにする（サロゲートIDを足すと誰も使わない列と余分な索引が1本増える） | (market, ticker) の複合自然キー／全テーブル一律のサロゲートID |
| サロゲートIDは識別列（`GENERATED ALWAYS AS IDENTITY`。DBが必ず自動で採番し、書き込む側からのID指定を受け付けない列） | `serial` は `INSERT ... VALUES (999, ...)` のようなID明示指定を黙って通し、採番用の数値は進まない。採番が999に達した日に重複キー違反で止まる。識別列は明示指定自体をエラーにするのでこの事故が構造的に起きない。PostgreSQL 10以降の公式推奨でもある | `serial` |
| エンティティ名は `stock` | `symbol`/`ticker` は識別子文字列の名前であり実体の名前ではない。`instrument`/`security` は債券・オプションまで含む過剰な抽象 | `symbol`・`ticker`・`instrument`・`security` |
| ISINは持たない | 人力登録の間、突合すべき外部データが存在しない。連携時に列を1本足せば済む | ISIN列の先行追加 |
| `event.market` に `GLOBAL` という明示値 | NULL=「全員」にすると `market='JP' OR market IS NULL` が全クエリに漏れる。FOMC・米CPI・米雇用統計は日本株保有者にも効くため `GLOBAL` | NULLを「全員」の意味に使う |
| イベントの対象は `event` 自身の3列（`market`/`theme_id`/`stock_id`）の排他 | `target_type`+`target_id` のポリモーフィックはFKが張れず、参照先が消えた行（削除済みテーマを指す行）を防げない。**中間テーブル（`event_target`）にすると、`market` と対象の排他が2テーブルにまたがり、CHECK制約だけでは書けなくなる**（対象の追加・削除を後から検査するトリガーが要り、しかも「対象0件かつ`market` NULL」＝誰にも表示されない行は防げない）。3列を同じ行に並べれば `CHECK (num_nonnulls(market, theme_id, stock_id) = 1)` の1行で表現できる。**引き換えに、1イベントの対象はちょうど1つに限られる**（表現できなくなるものは → §5.0.1）。これが未決事項 #5 の決着（→ §14） | ポリモーフィック関連／中間テーブル `event_target`（nullable FK 2列 + CHECK） |
| 対象の3列は `text` + CHECK で持つ（`market`）。PostgreSQL の列挙型は使わない | `stock.market`(JP/US) と `event.market`(JP/US/GLOBAL) を別の列挙型にすると**型が違うため比較できず**、種別ごとの判定で突き合わせられなくなる。1つの列挙型に統合すると比較は通るが、PostgreSQL の列挙型は値を削除できない（`ALTER TYPE ... DROP VALUE` が存在しない）ため値の変更が型の作り直しになる。`text` + CHECK なら CHECK の付け替え1回で済み、TypeScript 側の型は Drizzle の `text({ enum: [...] })` でユニオン型になるので失うものがない | PostgreSQL の列挙型（2つに分ける案・1つに統合する案とも） |
| 日付は3列（start/end/time） | 期間（3日間の会議）・時刻付き（FOMC）を単一 `date` 列では表せない。単日は `end_date IS NULL` で表し、`end_date = start_date` は CHECK で禁じる（単日の表現を1つに固定するため） | 単一 `date` 列／`precision`(day/month) 列の追加 |
| `precision`(day/month) 列は作らない | 現実の粒度は「上旬・中旬・下旬」「秋」「年内」まで幅があり、2値では表しきれない。格納規則も描画規則も未定義（旧・未決事項 #6）で読み手がいない。決算日は発表の約1か月前に確定し、日銀・FOMC・内閣府の指標はもともと日付確定で公表されるため、**日付確定後に登録する運用**（→ §4.1）で実用上足りる。必要になった時点で実データの粒度に合わせて設計し、列追加＋既存行を全て `day` にする1マイグレーションで足せる | `precision`(day/month) 列 |
| `ticker` に形式制約 `^[0-9A-Z.-]+$` | 日本語入力から全角の「７２０３」が入ると半角の「7203」と別銘柄として UNIQUE を素通りし、保有とイベントが2つの銘柄に割れる。後から気づいても紐付け直しは手作業になる | 形式を制約しない |
| 「日付未定」はDBの状態にしない | 月すら分からないイベントはカレンダーに描く場所がない。登録しない | `date` をNULL可にして「未定」を表す |
| `event.source` は作らない | 書き込む経路は `pnpm import:stat` が入って2つになったが（→ §2.1）、manual と auto を区別して使う場面がまだ無い。要るようになった時点で1マイグレーションで足せる | 出所列の先行追加 |
| `stock.fiscal_month` を持つ | 権利確定日・配当落ち日は保存せず、決算月と営業日カレンダーから計算で出すため | 権利確定日をイベントとして保存 |
| `event.short_label` を持つ | iPhone縦のカレンダーセル幅は約44pt。日本語のイベント名は入らない。機械的な短縮は不可（「令和9年度予算概算要求」→「令和9年度…」で意味が消える）。人力登録なので登録者が略号を付ける | タイトルの機械的短縮 |
| `event.importance`（★1〜3） | 「今週は荒れるか」に答える唯一の手段。Investing.com・TradingView・みんかぶで事実上の標準表記。人力登録の1カラムで済む | 重要度なし |
| `event.source_url` を持つ（`event.source` は作らないまま） | **上の「`event.source` は作らない」と矛盾しない。別物である。** `source` は取り込み経路の区分（manual/auto）で、後から足しても既存行に正しい値を入れられる。`source_url` は「この日付をどこで確認したか」の記録で、**後から列を足しても、それまでに登録したイベントの出典は復元できない**。用途は権利の照会と誤登録の追跡で、どちらも**運用者が見る**。<br>**出典の記載が条件の出典への対応は、この列だけでは果たせない。** 記載は利用者に見える形で出すことを求めるもので、`source_url` はアプリに届かない。**そのため `source_name` を別に足し、名前とURLが揃った行だけをアプリに返す**（→ [出典表示設計書](2026-08-11-41-event-source-design.md)）。`source_url` だけの行は運用者の記録として残り、画面には出ない | 出典を残さない |
| 作成者の列（`created_by`・`updated_by`）は作らない | **行を消せば列も一緒に消える**ので「誰が何を消したか」は出せない。監査ログがあれば作成者も貢献度も削除も全部出せるため、列を足しても監査ログは要る。逆は成り立たない | 5テーブルに `created_by`・`updated_by` を足す |
| 削除は行を消す。`active=false` にする「行を残す削除」は採らない | 5つのテーブルに列を足すと、**全部の問い合わせに絞り込みが漏れる**。上の `event.market` の NULL と同じ形の危うさ。監査ログは既存の問い合わせを1つも変えず、`previous_values` から `jsonb_populate_record` の1文で戻せる（→ [監査ログ 設計書 §5.4](2026-08-14-82-multi-editor-audit-design.md)） | 論理削除（`deleted_at` 列・`active` 列） |
| 監査ログはDBのトリガーではなくアプリで書く | `server/drizzle/` にトリガーが1つも無く、drizzle-kit は生成しない。手書きのSQLが `schema.ts` の外に住むことになる（`event_target` を却下したときと同じ理由）。書き込みの経路は2つしか無く、3つ目が増えたら落ちるテストで固定できる | DBのトリガーで自動記録 |
| 全テーブルに `created_at` を持つ | 同じ非可逆性。後から足しても過去行は空のまま。障害・問い合わせ調査の最低限の手がかりになる | 作成日時を持たない |

## 5. イベントの3種別と表示ルール

種別は `event` の対象3列のうち**どれが埋まっているか**で決まる。**種別ごとのテーブルは作らない。種別を宣言する列も作らない。**

| 種別 | 埋まっている列 | 誰に出るか | 例 |
|---|---|---|---|
| 市場イベント | `market` | `event.market` と保有銘柄の市場で判定（`GLOBAL` は全員） | FOMC(GLOBAL)・日銀会合(JP)・米予算(US) |
| テーマイベント | `theme_id` | そのテーマの銘柄を持つ人 | ドローンドミナンス採用決定 |
| 銘柄イベント | `stock_id` | その銘柄を持つ人 | 7203 の決算発表日 |

上の表はデータモデルが何を表せるかを示すもので、3種別すべてを今すぐ登録できるという意味ではない。登録できるかどうかは**日付をどこで確認するか**で決まる（→ §5.1）。

| 種別 | 今すぐ登録できるか | 日付の出典 |
|---|---|---|
| 銘柄イベント | できる | 各社のIRページ |
| テーマイベント（銘柄の出来事をテーマに寄せたもの） | できる | 各社のIRページ。下の「1つの出来事は必ず1行で登録する」で作るのがこれにあたる |
| テーマイベント（テーマ固有の出来事） | できない | 無い。例の「ドローンドミナンス採用決定」がこれ |
| 市場イベント（経済指標の公表予定） | できる | 日本は内閣府・省庁、米国は BLS（CPI・雇用統計）。どちらも出典をシートに出すのが条件 |
| 市場イベント（FOMC） | できる | FRB。出典をシートに出すのが条件 |
| 市場イベント（日銀会合） | できない | 無い。日銀は商用が対象外 |

**「テーマイベントが登録できない」ではない。** 登録できないのはテーマ固有の出来事（政策・業界の発表）であって、銘柄の出来事をテーマに寄せたテーマイベントは各社IRだけで作れる。

**1つの出来事は必ず1行で登録する。行の複製は禁止。** 銘柄とテーマの両方に効かせたい出来事（例: NVIDIA決算を NVDA 保有者と半導体テーマ保有者の両方に出したい）は、その銘柄をテーマに入れて**テーマイベント1行**にする。`theme_stock` が多対多なので表示対象は漏れない。

複製を禁じる理由: 同じ出来事を2行に分けると、両方に該当するユーザーの画面で**1日2件までのセル枠を1つの出来事が食いつぶし、月サマリの件数も二重に数える**（→ §10.2）。2行が同じ出来事だとスキーマからは判別できない。代償は「NVDA保有者の画面で色が銘柄の琥珀ではなくテーマの紫になる」程度にとどまる。

#### 5.0.1 対象を1つしか持てないことの限界（承知のうえの制約）

**対象を1行の3列で表すため、1つのイベントが持てる対象はちょうど1つになる。** 上の回避策（テーマに寄せる）が効くのは「銘柄×テーマ」の組み合わせだけで、次の2つは**そのままでは表現できない**。

| 表現できない例 | 回避策 | 回避策の副作用 |
|---|---|---|
| 2銘柄に効く1つの出来事（例: A社とB社の資本業務提携の共同発表） | その2銘柄だけの専用テーマを作る | `theme.name` は全ユーザー共通の一覧に残り続ける。イベント1件のための使い捨てテーマが積もる |
| 2テーマに効く1つの出来事（例: AIと半導体の両方に効く輸出規制） | どちらかのテーマに寄せる／統合テーマを作る | 寄せなかった側のテーマだけを持つ人に出ない |

さらに、回避策でテーマに銘柄を入れると、**それ以降そのテーマのイベントが全部その銘柄の保有者に出続ける**。イベント1件のための所属追加が、恒久的に効いてしまう。

**この制約を承知のうえで採る。** 利用者が運用者1人の間は、自分の保有のどれかに付ければ表示は成立するため実害が出ない。実害が出るのは複数ユーザーへ公開したあとで、そのときは中間テーブルへ戻す判断をする（→ §4.2）。

**戻すときのコストは「スキーマ上は1マイグレーション」にとどまる点に注意する。** 3列を中間テーブルの行へ移す作業自体は機械的で、データも失われない。しかし上の回避策で作った専用テーマと、そのために足した `theme_stock` の行は**自動では元に戻らない**。回避策で運用した期間が長いほど、戻すときに「専用テーマをほどいて複数の対象に付け直す」手作業が増える。

**月の絞り込みは重なり判定で行う。** 「その月に始まるイベント」ではなく `start_date ≦ 月末 AND COALESCE(end_date, start_date) ≧ 月初`。前者だと 8/31〜9/1 のFOMCが9月のカレンダーに出ない。

### 5.1 データの出典ポリシー

**イベントの日付は、下の表で「使う」になっている出典でのみ確認する。出典は各社のIRページ1つだけから始め、必要になった時点で1つずつ増やす。**

各社IRを最初の1つに選ぶ理由は、**利用にあたっての条件が付かない唯一の出典**だからである。登録するのは「いつ発表するか」という事実の転記であり、しかも発信者自身が投資家に広く知らせるために出している情報なので、こちらの利用目的と衝突しない。

| 出典 | 可否 | 根拠・条件 |
|---|---|---|
| 各社のIRページ（決算発表予定の告知） | **使う** | 条件なし。事実の転記 |
| 日銀（決定会合日程・公表予定） | 使わない | 転載・複製は可能だが、**商用目的で転載・複製を行う場合は対象外**で、事前に情報サービス局へ相談が必要と公表されている。本アプリは広告で収益化する（→ §14 #3）ため商用にあたる。出所を明記しても使えるようにはならない |
| 日本の府省（経済指標の公表予定） | **使う** | 公共データ利用規約（第1.0版）。「商用利用も可能です」と明記されており、条件は出典の記載。出典はイベントごとに `source_name` と `source_url` を持ち、iOS のシートに出す（→ [出典表示設計書](2026-08-11-41-event-source-design.md)）。内閣府・総務省・財務省が同じ規約を採用していることを確認済み |
| FRB（FOMC日程） | **使う** | サイトの [Disclaimer](https://www.federalreserve.gov/disclaimer.htm) が「特に断りのない限り、Board のサイトの情報はパブリックドメイン（誰でも自由に使える状態）であり、許可なく複製・配布できる。出所として Board を記載してほしい」と公表している。**商用を外す記述は無い**（日銀と違う点）。条件は日本の府省と同じく出典の記載だけなので、既にある `source_name` と `source_url` でそのまま満たせる。日程は [FOMC カレンダー](https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm) にHTMLで出ており、機械で読める形（CSV等）は無いため手で登録する |
| BLS（米CPI・雇用統計の公表予定） | **使う** | [Copyright Information](https://www.bls.gov/opub/copyright-information.htm) が「BLS は連邦政府機関であり、刊行するものはすべてパブリックドメイン（以前から著作権のある写真・イラストを除く）。許可なく使ってよいが、出所として Bureau of Labor Statistics を記載してほしい」と公表している。条件は日本の府省・FRB と同じく出典の記載だけ。**エンブレムは登録商標なので使わない**（企業ロゴを使わないのと同じ扱い）。なお `bls.gov` はプログラムからのアクセスに 403 を返すため、公表予定はブラウザで開いて写す |
| JPX の決算発表予定日ページ | 使わない | JPX 自身が同じデータを**有料で再配信するサービスを販売している**。少数の手動確認と全銘柄の機械的転記は別物 |
| 株探・みんかぶ・Investing.com・TradingView 等 | 使わない | 各社の利用規約が情報の商用利用・第三者提供を禁止している。法律より先に規約違反で詰む |

**上の表の根拠になった条文は、原文のまま [出典の利用条件](../../reference/source-terms.md) に残してある。** 表の欄は要約なので、元のページが書き換わると判断の根拠がたどれなくなる。残しているのは「使う」になっている3つ（日本の府省・FRB・BLS）で、確認日と取得方法も併せて書いてある。

「今は使わない」は手順を踏めば使えるもの、「使わない」は使わないと決めたものを表す。**この表は許可リストではなく、どの出典をどう判断したかの記録である。** 出典を増やすときは行を足すのではなく、可否を書き換える。

#### 出典を増やすときの手順

1. その発信者が示している利用条件を読む
2. 条件があれば、満たす手段を**先に**決める（出所明記が条件なら、出所をどの画面に出すかを決めてから使う）
3. 上の表の可否を「使う」に書き換え、条件を根拠の欄に書く

#### この決め方の代償

**登録できるのは、上の表で「使う」になっている出典で日付を確認できる出来事だけになる。** 使えないものが残る。

| 登録できないもの | なぜ |
|---|---|
| 金融政策決定会合の日程 | 日銀は商用が対象外 |
| テーマ固有の出来事（政策・業界の発表） | 発信者ごとに条件を読む必要があり、まだ読んでいない |

**テーマイベントそのものが作れなくなるわけではない。** 決算のように各社IRで日付を確認できる出来事なら、それをテーマに寄せたテーマイベントとして登録できる（→ §5「1つの出来事は必ず1行で登録する」）。使えなくなるのは、対象が3種別のどれかという区分ではなく、**日付の出典が「使う」の出典に無い出来事**である。

出典を1つずつ増やすことにした当初の理由は、**出典を1つに絞ると、出典まわりで作るものが無くなる**ためだった。この前提は Issue #41 で変わった。出典の記載を条件とする内閣府・省庁を使うために、出典を利用者に見せる仕組みを作った。それでも1つずつ増やす方針は変えない。増やすたびに条件を読む手間は残り、実際に読んで初めて日銀が商用不可だと分かった。

**企業ロゴは使用しない**（銘柄名・企業名のテキスト表示は、事実を指すための表示であり問題にならない）。

法的な整理としては、①「8月5日にトヨタの決算」という**日付そのものは著作権の保護対象外**、②網羅的な決算カレンダーは選択・構成に創作性が認められにくく**データベースの著作物にもなりにくい**、とされる。ただし「著作権がない＝自由に写してよい」ではなく、大量のデッドコピーを不法行為と認めた判例がある。**実務上効く制約は著作権法ではなく各社の利用規約**であり、上表はその前提で作っている。

手で少量ずつ登録するという本設計の方式は、自動スクレイピングより**構造的に安全**である。この安全性は方式ではなく**出典の選び方**によって担保されるため、上表を運用ルールとして守ることが前提になる。

**上表が決めるのは「どの出典を使ってよいか」だけで、「どう取ってよいか」は §2.1 が決める。** 出典の選び方が安全性を担保するという上の一文は、取得を人がやるか機械がやるかによらず成り立つ。実際、上表で「使う」になっている出典のうち、配信されている構造化データで公表予定を出しているのは総務省統計局だけで、そこも出典の記載という条件は手で登録する場合と変わらない。

> この節の法的整理は法律家によるものではない。判断材料として書いている。

## 6. リポジトリ構成

```
<repo>/
├── openapi.yaml   ← パスとリクエスト・レスポンスの型の唯一の正（手書き）
├── ios/           ← Xcode プロジェクト（Swift + SwiftUI）
└── server/        ← Next.js（管理UI + API Route Handlers）
```

- **1リポジトリ**。pnpm workspace も Turbo も入れない。ただのディレクトリ2つ
- **理由**: Swift↔TS で型共有の自動検知が効かない以上、契約のズレを捕まえる手段は「同じPRで両側の差分が並んで見える」ことしか残らない。2リポジトリ分離はこの検知を失う
- **却下**: 既存の別プロダクト `kabu-legends`（株式スクリーニング）への相乗り。別プロダクトのため

## 7. 技術選定

| 項目 | 選定 | 理由 |
|---|---|---|
| iOSクライアント | Swift + SwiftUI | 開発者が既にSwiftUIでアプリを開発しており学習コストなし。UXが明確に良い。型共有が切れることは承知の上で受容 |
| パスとリクエスト・レスポンスの型 | `openapi.yaml` 手書き。iOS側は Apple公式 `swift-openapi-generator`（SwiftPMビルドプラグイン、生成物はコミットしない）、server側は `openapi-typescript` で型生成 | 契約が単一ソース。両側とも型ズレがコンパイルエラーになる |
| バックエンド | Next.js 単体（管理UI + Route Handlers 同居） | Hono分離はデプロイ・認証・管理対象が2倍になるのに得るものがない |
| ORM | Drizzle | `event` の対象3列の排他（`CHECK (num_nonnulls(...) = 1)`）を、スキーマ定義の中にそのまま書けるため。Prisma はスキーマで表現できないと公式が明言している。**この理由は「既存資産で既知だから」より強く、再検討は不要**（→ Issue #16） |
| DBの種類 | PostgreSQL | §4.2 の対象3列の排他が CHECK 制約に依存する。SQLite系（Turso・D1）は対象外 |
| **DBのサービス** | 本番は Supabase 東京（→ Issue #74）。無料プランのまま使い、**400MB に達したら Pro に上げる**（→ `docs/guides/backup.md` §4） | 開発は今までどおり Docker の PostgreSQL。載せ替えるかどうかは保留のまま。候補ごとの比較は Issue #16（クローズ済み）に残してある |

## 8. `openapi.yaml` とのズレの検知

`openapi.yaml` が契約の唯一の正。両側がそこから型を生成するため、ズレは次の表のとおりコンパイルで捕まる。

| ズレ方 | 検知 |
|---|---|
| `openapi.yaml` を変えた → Swift側が未追随 | `xcodebuild` でコンパイルエラー（ビルド時に再生成されるため、生成物のコミット忘れが構造的に起きない） |
| `openapi.yaml` を変えた → server側が未追随 | `tsc` でコンパイルエラー |
| server実装だけ変えて `openapi.yaml` を忘れた | `tsc` が落ちる（handlerが生成型に縛られるため） |
| 型は合うが実行時の値が違う | **検知しない**。契約テストは10エンドポイントには過剰なので入れない |

**却下**: 「サーバー実装からOpenAPIを自動生成」— 契約の正が実装側に移り、iOS側から契約をレビューできなくなる。

## 9. 認証

Better Auth 一本で両クライアントをまかなう。

| クライアント | 方式 |
|---|---|
| Web管理UI | Cookieセッション。Google でのログインとメール＋パスワードの両方（→ `docs/guides/google-oauth.md`） |
| iOS | **ログインしない**（→ [ログイン廃止 設計書](2026-08-14-86-no-login-design.md)） |

- **iOS にログインは無い。** 持ち株は端末（`UserDefaults`）に置き、イベントの絞り込みも端末で行う。サーバーは誰が見ているかを知らない。`GET /api/events` と `GET /api/stocks` は認証を要求せず、誰が呼んでも同じ配列を返す
  - Better Auth の Bearer プラグインは iOS のためだけに入れていたので、一緒に外した。セッションは Cookie だけになった
  - メール＋パスワードは管理UIに残す。Google の設定が壊れた日に入る手段（`app/signin/signin-form.tsx`）
- **`user` テーブルは自作しない。Better Auth が生成するものをそのまま本設計の `user` とする**（未決事項 #9 の決定）
  - 根拠: `user` は入力者と監査ログを結ぶ表である。別テーブルで作って後から統合するとFK張り替えとデータ移行が発生するが、今なら判断1つで済む
  - 引き換えに、Better Auth のスキーマ都合（列名・マイグレーション）に本設計のFKが縛られる。これは受け入れる
- サインアップ無効。利用者は入力者ぶんを手動投入する（環境変数 `SEED_USERS` に JSON の配列で書く。→ [入力者を3人にする・監査ログ 設計書](2026-08-14-82-multi-editor-audit-design.md)）。**利用者を作れるのは `pnpm db:seed` だけ**で、
  Better Auth を通る作成（メール＋パスワードのサインアップ、Google の初回サインイン）は
  `databaseHooks.user.create.before` が全部拒む。プロバイダごとの `disableSignUp` では
  塞ぎきれない経路があるため（→ `docs/guides/google-oauth.md`）
- **役割は管理者と入力者の2つで、`user` の列にしない。** 環境変数 `ADMIN_EMAIL` に管理者のメールアドレスを1つ置き、セッションのメールアドレスと比べる（大文字小文字は問わない）
  - 根拠: `user` は Better Auth の生成物で、`pnpm auth:gen` が `src/db/auth-schema.ts` を作り直すため、手で足した列は消える。生成に含めるにはプラグインが要り、役割以外の列（利用停止・停止理由・期限）も付いてくる。3人の間は設定1つで足りる
  - `ADMIN_EMAIL` が未設定だと `app/actions.ts` が読み込みの時点で落ちる。誰も管理者にならず削除が全部拒まれる状態に、気づかないままなるのを防ぐ
  - **管理者だけができるのは削除4つ**（銘柄・テーマ・テーマ所属・イベント）。削除は取り返せないため。登録と編集は3人ともできる
  - 拒み方は**エラー文の文字列を返す**（`redirect()` にしない）。削除は成功しても `redirect("/")` するため、拒否を `redirect()` にすると成功と同じ `NEXT_REDIRECT` になり、拒まれたことを画面でもテストでも見分けられない（実測。→ [入力者を3人にする・監査ログ 設計書](2026-08-14-82-multi-editor-audit-design.md) §4）
  - 画面から削除の欄は消していない。判定はサーバー側にあり（Server Action は画面を通さず直接POSTできる）、押したときにエラー文が出る。管理者を増やすときは `ADMIN_EMAIL` を変えて配信し直す
- **Better Auth が生成する4テーブルの日時列はタイムゾーンなし**（自前テーブルの `created_at` はタイムゾーン付き）。生成物のため合わせに行かない。`session.expires_at` の解釈がサーバーのタイムゾーン設定に依存する点だけ、配信先を変えるときに確認する
- SwiftにSDKは不要。アプリが叩くのは `GET /api/events` と `GET /api/stocks` の2本だけ

## 10. iOSメイン画面のUI

**等高の月グリッド ＋ 日付タップで下からせり上がるボトムシート。**

### 10.1 構成

| 部分 | 使うもの |
|---|---|
| グリッド | `ForEach(weeks)` ＋ 週ごとの `HStack`（42セルを単一 `LazyVGrid` に流さない。週単位にしておくと後の変更が効く） |
| シート | ~~`.sheet(item:)`~~ **`.sheet(isPresented:)`** ＋ `.presentationDetents([.fraction(0.45), .large])`。`item` は日付が変わるたびにシートを出し直し、0.45 で開いていたシートが `.large` に広がってしまう（実機で確認。→ [ボトムシートと月サマリ設計書](2026-08-10-9-ios-sheet-summary-design.md) §3） |
| シート裏の操作 | `.presentationBackgroundInteraction(.enabled(upThrough: .fraction(0.45)))` ← シートを開いたまま別の日付をタップできる |
| 月の移動 | `TabView(.page)` の横スワイプ |

### 10.2 セル表示の規則

| 規則 | 内容 |
|---|---|
| 短縮ラベル | セルに出すのは全角4〜5文字まで。銘柄は `7203決算`、テーマは `ドローン`、市場は `日銀`／`米CPI`。正式名称はシートにだけ出す |
| 1日の上限 | セルに出すのは2件まで。3件目以降は `+1`。タップでシートに全件 |
| 色は種別だけ | 銘柄＝琥珀／市場＝藍／テーマ＝紫。色に重要度を持たせない（1つの色に2つの意味を持たせると両方読めなくなる） |
| 重要度は形 | ★3のラベルだけ左端に赤の細線と太字。★1・★2は差をつけない。44pt幅に★3つは描けないため、セル上は「注意すべきか否か」の2値に落とし、★の実数はシートで出す |
| 月サマリ | 上部に `7件 ・ ★3が2件` を常設。グリッドを読む前に「今月は荒れるか」に答える |

### 10.3 選定の経緯

実在アプリを2方向（一般カレンダーアプリ／金融・投資アプリ）から調査した結果、**金融イベント系アプリは揃って日付順アジェンダリストに収斂しており、月グリッドを主画面にしている例は発見できなかった**（Stock Events・TradingView・Investing.com・Delta・Earnings Whispers。moomooですら縦持ちは週表示）。調査上の推奨はアジェンダリスト（週ストリップ＋★＋対象チップ）だった。

**それを踏まえたうえで、開発者の判断で月グリッドを採用した。** 短縮ラベルとボトムシートの組み合わせにより、月グリッドの弱点（セル幅・1日3件以上・空白の週）に対処する設計になっている。

この経緯を残す理由は、将来「なぜ業界標準と違う形なのか」を再検討できるようにするため。第2の選択肢（アジェンダリスト、および銘柄軸の逆引きビュー＝Seeking Alphaのポートフォリオ Earnings タブに実在）は、必要になった時点でタブを1つ増やすだけで足せる。

### 10.4 マスコットキャラクター

**「ケッサンショウオ」を採用する。**

| 項目 | 内容 |
|---|---|
| 名前 | ケッサンショウオ（表記は `ウ` を1つ落とした8文字。鳥取県日南町「オッサンショウオ」と同じ詰め方） |
| 由来 | 決算 → ケッ**サン** → **サンショウウオ**（オオサンショウウオ）。音が完全に重なる掛詞 |
| 見た目 | ずんぐりしたオオサンショウウオ。ぶち模様の茶色、半開きの目、への字口。カレンダーの上に岩のように寝そべり、イベントが近づくと目だけ開く |

キャラクターと機能の対応:

| 特性 | 対応する思想 |
|---|---|
| じっと動かない | **売買しない・予測しない**。予定を並べるだけ（→ §1・§2） |
| ずっと見ている | イベントを見張る＝本アプリの主機能 |
| 生きた化石・特別天然記念物 | 慌てず長期で構える |

参照した型は配当管理アプリ「ハイトン」（配当 → ハイトウ → **トン（豚）**、豚＝貯金箱＝お金が貯まる）。この型で本質的に効くのは音の掛詞ではなく、**着地先の動物が機能の比喩を持っていること**。ケッサンショウオは「動かない」という一般には弱点となる特性が、本アプリでは思想そのものになる点で条件を満たす。

**却下した案**: カブケン（株券 → 犬。番犬＝見張って知らせる。型への忠実度は高いが、犬キャラは世に多く造形での差別化が要る）、カブスキ（「スキ」から動物が導けず、キャラが生まれない。「スキー＝滑る」への着地は投資アプリとして縁起が悪い）、カブラッコ・コヨーミ・ヨーテイ（ヨーテイは PS5『Ghost of Yōtei』と音が完全一致し埋没する）。

## 12. 初回リリースに含めないもの

| 項目 | 理由 |
|---|---|
| リモートプッシュ通知（APNs） | サーバー側基盤が重い。ローカル通知で足りるか先に検証 |
| ホーム画面ウィジェット | 価値は高いが「開いて見る」体験の検証が先 |
| EventKit で標準カレンダーへ書き出し | 標準カレンダーに出すなら本アプリ不要説すらある。検証後に判断 |
| SwiftData / オフラインキャッシュ | 数KBのデータに永続化層は過剰 |
| リフレッシュトークン / JWT基盤 | iOS にログインが無いので、そもそも要らない（→ §9） |
| サインアップ | 画面から利用者を作れるようにはしない。利用者は管理UIの入力者だけで、アプリの利用にアカウントは要らない。**入力者が3人になったため、複数の利用者を `pnpm db:seed` で作れるようにした**（→ [入力者を3人にする・監査ログ 設計書](2026-08-14-82-multi-editor-audit-design.md)）。役割は管理者と入力者の2つで、管理者だけが削除できる |
| 銘柄軸の逆引きビュー（第2タブ） | 第1タブが動いてから足せる |
| 重要度以外のフィルタ・ミュート・テーマ階層 | 利用者=運用者=自分の間は不要 |
| 広告（AdMob バナー） | 利用者が自分1人の間は収入が0円なのに、ATTの同意ダイアログ・App Privacy の申告・SDKの依存・審査リスクだけを先に背負うことになる（→ §14 #3） |

**額の見積もりよりも先に効く事実**（Issue #16 の調査で判明したもの）:

| 事実 | 効き方 |
|---|---|
| **Vercel Hobby は非商用限定** | 広告・アフィリエイト・**寄付まで**商用扱い。「収益化が目的」（→ §1.1）と決めた時点で、**Vercel の**無料枠は選択肢から外れる。無料枠がすべて非商用限定なわけではなく、商用可のものもある（Issue #16 参照） |
| **無料枠のマネージドDBは定期バックアップを持たないことが多い** | 週1回の `pg_dump` が要る（→ §14「運用」） |
| **無料枠には「一定期間アクセスがないと止まる」ものがある** | 1日1回開くアプリと相性が悪い。選定時の判定条件になる |

**課金に切り替える場合の注意（特定商取引法）**: アプリ内課金でも表示責任は開発者が負う。**氏名は省略できない**（個人事業者は戸籍上の氏名、または商業登記した商号。屋号やサイト名だけでは足りない）。一方**住所と電話番号は省略できる**。「消費者から請求があれば遅滞なく提供する」と広告に書き、実際にそうできる状態にしておけばよい（消費者庁の通信販売広告Q&A）。**つまりバーチャルオフィスは必須ではなく、課金に切り替える判断のコストは「本名を公開できるか」の1点に絞られる。** ただし請求が来れば住所を伝えることになるため、それを避けたい場合に初めてバーチャルオフィス等を検討する。広告だけの場合は消費者への販売がないため、この節は適用されない（→ §14 #3）。

### 投資助言との境界（#13 の具体化）

投資助言・代理業の登録が必要になるのは、おおむね **①報酬を得て ②契約に基づき ③個別性のある助言をする** 場合とされる。不特定多数向けに誰でも同じ内容を入手できる形で提供される投資情報は、登録不要の側に整理される（雑誌の株特集が規制されないのと同じ理屈）。

| 要素 | MVP | 将来の「似た持ち株の人が買っている銘柄」機能 |
|---|---|---|
| 個別性 | **なし**。全員に同じ予定表が出る | **あり**。登録した銘柄によって出力が変わる |
| 報酬性 | **なし**。無料 | 有料機能にすれば **あり** |
| 契約 | なし | なし |

**危険水域は「個別性のある提示」と「有料化」が揃ったとき。** 特に「基本は無料、似た人の銘柄だけプレミアム」という形は、対価と個別提示が直結するため最も危うい。広告収入のみの場合は助言の対価ではないぶん弱いと考えられるが、**ここは未確認**。

**設計で弱められる。** 同じ情報でも見せ方で性格が変わる。

| 見せ方 | 性格 |
|---|---|
| 「6920 を買うとよいでしょう」 | 明確に助言 |
| 「似た保有の人の62%が 6920 を持っています」 | **事実の提示**。判断は本人がする |

**この機能の設計に着手する時点で、①有料にするか ②どちらの言葉づかいにするか の2つを先に決める。** 専門家への確認もそのタイミングで行う。それ以前は不要。

> この節の法的整理は法律家によるものではない。判断材料として書いている。

### 運用（公開とは無関係に今から必要）

**週1回の `pg_dump` を取る。** 人力登録したイベントは製品の中身であり、消えたら再入力するしかない。**トリガーは「公開」ではなく「データを貯め始めた日」。** 手順は `docs/guides/backup.md`（コマンドは `pnpm db:dump`。→ Issue #81）。

**選んだ先（Supabase の無料プラン）に定期バックアップは無かった**ので、自分で取り続ける。Pro（$25/月）に上げると日次で7日ぶん保持されるため、上げたときに見直す（上げる線は `docs/guides/backup.md` §4）。

**毎年2月、`server/src/rights.ts` の休場日リストに翌年ぶんを足す。** 権利付最終日はこのリストから計算しており（→ §14 #7）、載っていない年は計算しない作りになっている。**足し忘れると、カレンダーから権利日が黙って消える**（エラーにはならない）。

2月にするのは、**翌年の祝日が前年2月の官報で確定するため**（春分・秋分の日は天文計算の結果が公表されるまで決まらない）。確定したらすぐ足す。年の後半まで待つと間に合わない。カレンダーが出す範囲は起動月の前後12ヶ月なので、**年が明ける前から翌年ぶんが必要になる**。具体的には、Y年M月の時点で「決算月がM以下の銘柄」についてY+1年ぶんが要る。

**この運用でも埋められない期間が残る。** 1月決算の銘柄は、Y年1月の時点でY+1年ぶんが要るのに、Y+1年の祝日はその翌月（Y年2月）まで確定しない。**1月決算の銘柄は毎年1月のあいだ、翌年の権利日が出ない。** 推測で埋めない方針（→ §14 #7）を採る以上、ここは空欄のままにする。
