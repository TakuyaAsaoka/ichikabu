## 1. 目的と結論

**月グリッドに「日付タップで開くボトムシート」と「月サマリ」を足し、全体設計書 §10 のメイン画面を完成させる。**

Issue #8 でセルの表示は「短縮ラベル2件まで、3件目以降は `+N`」になった（§10.2）。いま**3件目以降を見る手段が画面に存在しない**。正式名称と★の実数も、セルには出さないと決めた分がどこにも出ていない。シートがその受け皿になる。

| 項目 | 決定 |
|---|---|
| ファイル | 新規なし。`EventLayout.swift` と `CalendarView.swift` に足す（→ §2） |
| シートの出し方 | `.sheet(item:)` ＋ `.presentationDetents([.fraction(0.45), .large])`（→ §3） |
| 0件の日のタップ | **シートを開き「イベントはありません」と出す**（→ §3） |

新規ファイルは作らない。Issue #8 設計書 §2 判断7 が「1画面に4ファイルは過剰」としてセル・週・月の分割を却下しており、その判断をそのまま引き継ぐ。

| ファイル | 追加するもの |
|---|---|
| `ios/Ichikabu/EventLayout.swift` | 月サマリの集計（純関数。→ §5）、シートの見出しの文字列 |
| `ios/Ichikabu/CalendarView.swift` | セルのタップ、`.sheet`、シートの中身（private struct）、月サマリの表示 |
| `ios/IchikabuTests/EventLayoutTests.swift` | → §6 |

**その日のイベントを選ぶ関数は既にある。** `EventLayout.events(on:from:)` をセルとシートの両方から呼ぶので、セルに出るものとシートに出るものが構造的にずれない。

## 3. シート

### 開き方

`.sheet(item:)` は `Identifiable` を要求するが、日付キーは `String` で `Identifiable` ではない。`Date` を包んだ小さな型を作り、**日付キーをそのまま `id` にする**。

```swift
struct SelectedDay: Identifiable {
    let date: Date
    var id: String { EventLayout.key(for: date) }
}
```

`Date` を持つのは見出し（`8月4日（火）`）に曜日が要るため。`id` の側は `EventLayout.events(on:from:)` にそのまま渡せる。

```swift
.sheet(item: $selectedDay) { day in
    DaySheet(date: day.date, events: EventLayout.events(on: day.id, from: events))
        .presentationDetents([.fraction(0.45), .large])
        .presentationBackgroundInteraction(.enabled(upThrough: .fraction(0.45)))
}
```

`.presentationBackgroundInteraction` は、シートを 0.45 まで下げている間だけ裏の操作を通す（全体設計書 §10.1）。これで**シートを開いたまま別の日付をタップできる**。

### 既知のリスク: `.sheet(item:)` の再提示

`.sheet(item:)` は `item` の `id` が変わったとき、シートを閉じて開き直す挙動になることがある。そうなると完了条件「シートを開いたまま別の日付をタップすると、シートの内容がその日付に切り替わる」が、閉じる→開くのアニメーションを挟む形になる。

**まず全体設計書 §10.1 の指定どおり `.sheet(item:)` で実装し、シミュレータで見て判断する**（→ §7 手順3）。切り替えが成立しないなら `.sheet(isPresented:)` ＋ 表示中の日付を持つ別の `@State` に変える。その場合は §10.1 の記述と食い違うので、全体設計書の側も直す。

### どの日でタップを受けるか

| 日 | タップ |
|---|---|
| 表示中の月の日（イベント有無を問わない） | **開く** |
| 42セルの前後の埋め草（月外の日） | **効かせない** |

埋め草を効かせないのは、Issue #8 設計書 §2 判断9 でその日のイベントを出さないと決めているため。イベントを出していない日をタップして中身が出ると、セルとシートで見えるものが食い違う。

**0件の日もシートを開く。** Issue #9 の補足はこれを実装者の判断に委ねている（「シートを開かない、または空のシートを開く」）。開かない方を採らないのは、**シートを開いたまま0件の日をタップしたときにシートが消える**ためで、同じ操作の結果が日によって「切り替わる」と「閉じる」に分かれるのは挙動として読みにくい。

### 中身

見出しは `8月4日（火）`。その下にその日の全件を、`EventLayout.events(on:from:)` が返す順（APIの並び順）で縦に並べる。**セルで `+N` に省略された分もここに出る。**

| 出すもの | 形 | 根拠 |
|---|---|---|
| ★の実数 | `★★★` / `★★` / `★`（`String(repeating:)`） | §10.2「★の実数はシートで出す」。セル上は「★3か否か」の2値に落としてある |
| 正式名称 | `title` | §10.2「正式名称はシートにだけ出す」 |
| 短縮ラベル | 種別の色（`EventLayout.color(for:)`）を付ける | 色で銘柄／市場／テーマが分かる。セルと同じ対応付けを使う |
| 時刻 | `time` があるときだけ | 空にできる（全体設計書 §4.1） |
| 補足 | `note` があるときだけ | 同上 |

0件のときは「イベントはありません」の1行。

`source_url` は出さない。`openapi.yaml` の `Event` に入っておらずアプリに届かない（全体設計書 §4.2）。

## 4. 月サマリ

グリッド上部、月タイトルの下に `7件 ・ ★3が2件` を常設する（§10.2）。

**イベントが0件の月も同じ形で `0件 ・ ★3が0件` と出す。** 文言を分けない。「今月は荒れるか」に先に答えるのがこの表示の役目で、0件はその答えの1つである。表示を消したり文言を変えたりすると、月を送ったときに行の高さが変わってグリッドが縦にずれる。

## 5. 月サマリの数え方

```swift
static func summary(forMonthOf monthStart: Date, from events: [Event])
    -> (total: Int, importantCount: Int)
```

**その月に重なるイベントを数える。** 月初と月末の日付キーを作り、`startDate <= 月末 && (endDate ?? startDate) >= 月初` に当たる件数を返す。全体設計書 §5「月の絞り込みは重なり判定で行う」と同じ式で、`EventLayout.events(on:from:)` が日について使っている式を月に広げただけになる。

| 論点 | 決定 |
|---|---|
| 月をまたぐ期間イベント（8/31〜9/1） | **両方の月で1件ずつ**数える。セルには各日に出るが、出来事としては1件 |
| 同じ月の中の期間イベント（9/16〜9/17） | **1件**。セルには2日に出るが二重に数えない |
| 埋め草のセルに出ていないイベント | 数に入らない。埋め草は月外の日なので、重なり判定にも当たらない |

「セルに出た回数」ではなく「出来事の数」を数える。全体設計書 §5 が行の複製を禁じている理由（1つの出来事を2件と数えない）と同じ考え方で、期間についても同じ扱いにする。

グリッドは6週42セルなので前月末・翌月頭の日も描かれるが、そこにイベントは出さない（Issue #8 設計書 §2 判断9）。**その判断の理由が「月サマリの件数と食い違って見える」ことだった**ので、ここで数え方を月の重なりに揃えると前提が合う。

## 6. テスト

`ios/IchikabuTests/EventLayoutTests.swift` に4件足す（現在9件 → 13件）。テストケース名は日本語。

| # | テスト | 固定する挙動 |
|---|---|---|
| 1 | 月サマリはその月に重なるイベントを数える | 前月・翌月のイベントが混ざらない |
| 2 | 月をまたぐ期間イベントは両方の月で1件と数える | 8/31〜9/1 が8月でも9月でも1 |
| 3 | 月サマリは★3の件数を別に数える | ★3が2件、★1・★2は `importantCount` に入らない |
| 4 | イベントが無い月は0件になる | 総数も★3も0 |

シートの中身は SwiftUI のビューなのでテストしない。**シートに出す内容を決める部分（その日のイベントの絞り込み）は `EventLayout.events(on:from:)` で、Issue #8 のテストが既に4件で固定している。**

## 7. 確認手順

### 手順1: 品質ゲート

`ios/` で `xcodebuild build test -scheme Ichikabu -destination 'platform=iOS Simulator,name=iPhone 17' -skipPackagePluginValidation` が成功すること。警告0件。

server 側は変更しないが、目視確認のために起動する。

### 手順2: 確認用データを足す

seed に入るのは単日の銘柄イベントだけ（Issue #8 設計書 §3）で、**期間イベントが1件も無い**。§5 の「月をまたぐ期間」と、シートに期間イベントが各日出ることを目で見るには足りない。

**管理UI（Issue #7 で作った登録画面）から期間イベントを1件登録する。** シミュレータでの確認のために作るデータなので、出典ポリシー（全体設計書 §5.1）に沿って実在の日付を使うか、確認後に消す。消す前提で入れるなら `note` にその旨を書く。

### 手順3: シミュレータでの目視

1. `server/` で `docker compose up -d --wait && pnpm db:migrate && pnpm db:seed`、`pnpm dev` で起動する
2. シミュレータでサインインし、8月のページを開く
3. **8/4 のセルをタップ** → シートが 0.45 で開き、**3件すべて**（セルでは `+1` に省略されていた分を含む）が正式名称で出ることを確認する
4. シート内で★が `★★★` `★★` `★` と実数で出ることを確認する
5. **シートを開いたまま別の日付をタップ** → シートの中身がその日に切り替わることを確認する（→ §3 の既知のリスク）
6. イベントの無い日をタップ → 「イベントはありません」が出ることを確認する
7. シートを上にドラッグ → `.large` まで広がることを確認する
8. グリッド上部に `3件 ・ ★3が1件` が出ること、月を送ると数字が変わることを確認する
9. 手順2 で入れた期間イベントの各日のセルをタップし、どの日のシートにも出ることを確認する

結果をこの節に表で追記する。

## 8. やらないこと

| 対象 | 理由 |
|---|---|
| フィルタ・ミュート | 全体設計書 §12 |
| `+N` だけを個別にタップする反応 | セル全体のタップでシートが開き、そこに全件出る。`+N` に別の反応を付けても行き先が同じ |
| シートからのイベントの編集・削除 | 登録・編集は管理UIの担当（管理UI設計書 §12）。アプリは読むだけ（全体設計書 §2） |

| `source_url` の表示 | APIに含まれない（→ §3） |
