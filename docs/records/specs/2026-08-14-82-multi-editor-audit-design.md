# 入力者を3人にする・監査ログ 設計書

対象 Issue: [#82](https://github.com/TakuyaAsaoka/ichikabu/issues/82)（入力者を複数人に）・[#83](https://github.com/TakuyaAsaoka/ichikabu/issues/83)（削除を管理者だけに）・[#84](https://github.com/TakuyaAsaoka/ichikabu/issues/84)（監査ログ）

## 1. 目的と結論

イベントの入力を本人＋2人の計3人で行う。そのために次の3つを入れる。

| # | やること | Issue |
|---|---|---|
| 1 | 入力者を複数人登録できるようにする | #82 |
| 2 | 削除を管理者だけに限る | #83 |
| 3 | 誰が作成・更新・削除したかを記録する | #84 |

**この3つの後に、管理画面を目的別に作り直す**（別の設計書にする）。管理画面は後から何度でも作り直せるが、3人が入力を始めた後の「誰がやったか」は二度と作れないため、記録が先になる。

**全体設計書 §12 の「サインアップ・複数ユーザー・ロールは初回に含めない」を一部変える。** §12 がそう決めた理由は「利用者は自分1人」であり、その前提が3人になって消えたためである。**サインアップを開くわけではない。** 利用者を作れるのは `pnpm db:seed` だけ、という §9 の決定は変えない。

## 2. 役割

| 役割 | 人数 | できること |
|---|---|---|
| 管理者 | 1（本人） | 全部。**削除もできる**。監査ログを見られる |
| 入力者 | 2 | 銘柄・テーマ・イベントの登録と編集。**削除はできない**（自分の保有を外すのは除く） |

削除だけを分ける理由は、削除が取り返せないためである。作成と編集は誰でも直せる。

保有を外すのを除くのは、保有が本人の行で、足し直せば戻るためである（→ §4）。

### 役割を `user` の列にしない

`user` テーブルは Better Auth が作るもので（§9）、`pnpm auth:gen` が `server/src/db/auth-schema.ts` を**生成し直す**。手で足した列は次の生成で消える。生成に含めるには Better Auth のプラグインを入れることになり、役割以外の列（利用停止・停止理由・期限など）も付いてくる。

**管理者のメールアドレスを設定に1つ置き、それと比べる。** マイグレーションも生成ファイルへの変更も要らない。3人の間はこれで足りる。管理者を増やすときは設定を変えて配信し直す。

## 3. 入力者を増やす（#82）

`server/scripts/seed.ts` が環境変数1組（`SEED_USER_EMAIL` / `SEED_USER_PASSWORD`）から1人だけ作っている。ここをループにする。

`server/src/db/seed-user.ts` の `seedUser(email, password)` は既に引数を取るので**中身は変えない**。同じメールアドレスで2回実行しても増えない判定も、そのまま効く。

`server/src/auth.ts` の `databaseHooks.user.create.before` は「利用者を増やす作成をすべて拒む」ままにする。`seedUser` はテーブルへ直接入れるのでこの判定を通らない。**画面から利用者を作れないことは変わらない。**

## 4. 削除を管理者だけに限る（#83）

`server/app/actions.ts` の削除は5つ（銘柄・保有・テーマ・テーマ所属・イベント）。今はどれも `requireUserId()` を呼ぶだけで、サインインしていれば誰でも実行できる。

`requireUserId()` の隣に管理者を確かめる関数を置き、**削除5つのうち4つ**（銘柄・テーマ・テーマ所属・イベント）がそれを呼ぶ。保有を外すのは含めない（理由はこの節の末尾）。

**画面から削除のリンクを消すだけでは足りない。** Server Action は画面を通さず直接POSTできる（`server/app/actions.ts` の `requireSession` に書いた注記と同じ理由）。判定はサーバー側で行い、テストも Server Action を直接呼ぶ形で書く。

管理者かどうかは、環境変数 `ADMIN_EMAIL` とセッションのメールアドレスを比べて決める。両方を小文字にしてから比べる（`seedUser` がメールアドレスを小文字にして入れるため、揃えないと設定に大文字が1つ入っただけで管理者が誰も居なくなる）。`ADMIN_EMAIL` が未設定なら `app/actions.ts` が読み込みの時点で落ちる。

### 拒み方はエラー文の文字列を返す

`redirect()` で追い返さない。**削除は成功しても `redirect("/")` するため、拒否も `redirect()` にすると成功と拒否が同じ `NEXT_REDIRECT` になり、見分けられなくなる。**

実測（2026-08-14）: 権限判定を1行も入れていない状態で `await expect(removeEvent(null, form)).rejects.toThrow(/NEXT_REDIRECT/)` を走らせると**緑**になり、そのときイベントは削除されていた（残った件数 0）。つまり `redirect()` 案では、拒まれたことを判定するテストが書けない。

戻り値のエラー文は、他の Server Action と同じ形で、`app/form.tsx` の `ActionForm` がそのまま表示する。新しい配線は要らない。

**画面から削除の欄は消さない。** 判定はサーバー側にあるので画面を変えても安全性は1ミリも変わらず、変えると削除しか置いていない2ページ（`app/holdings/[stockId]/page.tsx`・`app/themes/[id]/stocks/[stockId]/page.tsx`）が空になり、`app/page.tsx` のリンクも道連れになる。押したときにエラー文が出れば、入力者には理由が伝わる。

### 保有を外すのは含めない（削除5つのうち4つ）

> **この節はもう当たらない。** [ログイン廃止 設計書](2026-08-14-86-no-login-design.md) §5.1 で `holding` テーブルごと消えたため、削除は4つになり、全部が管理者に限られる。`app/holdings/[stockId]/page.tsx` と `deleteHolding` も無い。当時の判断の記録として残す。

`deleteHolding` は `(user_id, stock_id)` で絞るため、**呼んだ本人の行しか消せない**（`src/db/write.test.ts`「他の利用者の保有は消えない」）。管理者に限ると、入力者が足した保有は管理者にも消せない行になり、`psql` を叩くまで残る。しかも `addHolding` は限らないので、増やせるが減らせない一方通行になる。

保有は足し直せば戻るので、削除を限る理由（**取り返せない**）そのものが当たらない。§2 の役割の表も、入力者にできることとして保有を挙げていない（触れていない）。

なお、管理者が**他人の**保有を外せる経路はもともと無い。これはこの Issue で増えた欠落ではなく、必要になったら別 Issue で足す。

## 5. 監査ログ（#84）

### 5.1 テーブル1本

`audit_log`

| 列 | 中身 |
|---|---|
| `user_id` | 操作した利用者。取り込みスクリプトなど人以外は空 |
| `action` | 作成・更新・削除の区分 |
| `resource_type` / `resource_id` | 何に対する操作か |
| `previous_values` | 変更前の行（更新・削除のとき）。jsonb |
| `new_values` | 変更後の行（作成・更新のとき）。jsonb |
| `created_at` | 記録した日時 |

- 主キーは識別列の連番（§4.2 で全テーブル統一済み。参考にした kabu-legends は uuid だが揃えない）
- **IPアドレスとブラウザの種類は持たない。** 身内3人で、追跡する相手がいない
- 索引3本: `created_at` / `user_id` / `(resource_type, resource_id, created_at)`

3本目が要る理由は、イベント一覧に「登録したのは誰か」を出すとき、そのイベントの作成の記録を引くためである。kabu-legends は `resource_type` だけの索引を張っているが、それでは行を引けない。

### 5.2 記録を差し込む場所は2つ

**書き込みの経路は2つあり、片方だけでは実データのほとんどが残らない。**

| 経路 | 位置 | 記録するか |
|---|---|---|
| 管理画面のフォーム14種 | `server/app/actions.ts` | する |
| 統計局の取り込み | `server/scripts/import-stat-schedule.ts` → `upsertMarketEvents` | **する**（利用者IDは空） |
| 開発用データの投入 | `server/src/db/seed-event.ts` | しない（固定値を入れるだけ） |

`upsertMarketEvents`（`server/src/db/write.ts`）は内部で登録・更新・非アクティブ化の3つをする。ここが漏れると「誰が消したか分からない更新」が残り、監査したい対象そのものを取り逃がす。

**3つ目の経路が増えたら落ちるテストを1本置く。** `src/db/write` を値として読み込んでよいファイルを、上の2つに固定する。今 `src/db/write` を読み込む11ファイルのうち、書き込み関数を呼ぶのはこの2つだけで、残りは型か `isId` の読み込みである（2026-08-14 に実測）。**2つしかないから固定できる。**

参考にした kabu-legends は、各操作が記録の関数を自分で呼ぶ形で、呼び忘れがそのまま漏れになる（別リポジトリ kabu-legends の `packages/api/src/index.ts` の `auditedProcedure`。記録するかどうかは各操作が呼ぶ `ctx.audit.setCreated` 等で決まる。2026-08-15 に実測）。この境界のテストは、その形を採らないためのものである。

### 5.3 行を返すようにする

`server/src/db/write.ts` の作成・更新・削除の関数は、どれも**行を返さない**（`.returning()` は `upsertMarketEvents` の3箇所だけ）。`run()`（92行）が結果を捨てている。

- `run()` を、返ってきた行も渡せる形に直す（変わる判定は1箇所）
- 削除5つ・更新3つの関数に `.returning()` を足す

これをしないと `previous_values` に入れる中身が取れず、`resource_id` も書けない。

### 5.4 消した行を戻す

`previous_values` に行をまるごと入れておけば、次の1文で元に戻る。**復元用の画面もコードも作らない。**

```sql
INSERT INTO event OVERRIDING SYSTEM VALUE
SELECT r.* FROM audit_log a, LATERAL jsonb_populate_record(NULL::event, a.previous_values) AS r
WHERE a.id = <監査ログのID>;
```

開発DBで実行し、`id` と `created_at` まで元通りに戻ることを確認した（2026-08-14）。識別列は `GENERATED ALWAYS` なのでそのままでは ID を指定できないが、`OVERRIDING SYSTEM VALUE` を付けると通る。

**銘柄とテーマの削除だけは追加の手当てが要る。** `theme_stock` が CASCADE で一緒に消え（`server/drizzle/0000_simple_blacklash.sql`）、その行はどこにも残らない。削除の中で `theme_stock` を先に消し、消した行を記録に含める。

### 5.5 作成者の列は作らない

`event.created_by` のような列を足しても、**行を消せば列も一緒に消える**ので「誰が何を消したか」は出せない。監査ログがあれば作成者も貢献度も削除も全部出せる。**列を足しても監査ログは要るので、列は要らない。**

貢献度は記録を数えれば出る。

```sql
SELECT COALESCE(u.email, '(取り込み)') AS 入力者,
       count(*) FILTER (WHERE a.action='create') AS 登録,
       count(*) FILTER (WHERE a.action='update') AS 更新,
       count(*) FILTER (WHERE a.action='delete') AS 削除
FROM audit_log a LEFT JOIN "user" u ON u.id = a.user_id
GROUP BY 1;
```

### 5.6 実装時に討論で決めた4つ（2026-08-14）

| 判断 | 結論 | 決め手 | 棄却した案 |
|---|---|---|---|
| `action` の値 | `create` / `update` / `delete` | §5.1 が対象を `resource_type` に分けて決めている。`create_event` にすると同じことを2列で言う | `create_event` のように対象を含める |
| `audit_log.user_id` の外部キー | `onDelete: "restrict"` | SET NULL は、入力者を1人消すと「取り込みがイベントを3件削除した」と読める行を作る（取り込みに DELETE は無い）。外部キー無しは実在しない利用者IDが黙って入る。restrict は両方を防ぐ。入力者をやめさせるのに `user` の行を消す必要は無い（→ §4.2 の表） | SET NULL／CASCADE／外部キーを張らない＋UUID形式の CHECK |
| 記録に失敗したとき | 書き込みは済んだと明記したエラー文を返す。取り込みスクリプトは投げる | `grep -rn "console\." app src` は0件、`netlify.toml` に転送の設定なし、監視の仕組みも無い。**握りつぶすと誰にも届かない。** `src/db/write.ts` の `run()` と取り込みスクリプトが同じ問いを2回「握りつぶさない」で決着させている | `console.error` だけ出して成功として扱う（kabu-legends の形）／書き込みと同じ取り引きに入れて巻き戻す |
| 監査ログを見る画面 | この Issue に含めない | psql で読める。§7 が「状態」画面として置き場所を予約している | `app/page.tsx` に抜けを数える1行を出す |

**記録に失敗したときの巻き戻しは構造上できない。** 記録は書き込みの後に走り、取り込みの記録は取り引きが確定した後に渡される。同じ取り引きに入れるには15の書き込み関数に `tx` と利用者IDを通すことになり、§6 が棄却した形になる。**止めるのは巻き戻すためではなく、記録が1件欠けたことを人に渡すためである。**

### 5.7 `previous_values` のキーはDBの列名にする

Drizzle が返す行のキーは `shortLabel` のような TypeScript 側の名前で、§5.4 の復元SQL（`jsonb_populate_record(NULL::event, previous_values)`）は**列名（`short_label`）でしか行を組み立てられない**。TypeScript 側の名前のまま入れると、名前の違う列が全部 NULL になり NOT NULL 違反で戻せない（実装時に実測）。

`src/db/audit.ts` の記録を作る3つの関数が、テーブルを受け取って `getTableColumns` でキーを列名に直す。`resource_type` も同じテーブルから取るため、対象の名前を手で書く場所が無い。

### 5.8 過去の行は諦める

開発DBの40件は、すべて `seed-event.ts` か取り込みスクリプトが入れたもので、**人が画面から入れた行は0件**である（2026-08-14 に実測）。したがって記録を今から始めても失うものは無い。**3人が入力を始める前に入れることが条件になる。**

## 6. 棄却した案

| 案 | 棄却の理由 |
|---|---|
| 削除を `active=false` にする（行を残す削除）＋ `created_by`・`updated_by` の列 | 5つのテーブルに列を足すと、**全部の問い合わせに絞り込みが漏れる**。§4.2 が `event.market` の NULL について同じ形を警戒している。監査ログは既存の問い合わせを1つも変えない |
| DBのトリガーで自動記録する | `server/drizzle/` にトリガーが1つも無く、drizzle-kit は生成しない。手書きのSQLが `schema.ts` の外に住むことになる。§4.2 が `event_target` を却下したときも「トリガーが要る」を理由の1つに挙げている |
| 記録を `src/db/write.ts` に置く | write.ts はDBだけを見る層で、誰が操作したかを知らない。14関数すべてに利用者IDの引数を足すことになる |
| 役割を `user` の列にする | `pnpm auth:gen` が生成し直すので消える（→ §2） |
| 記録を `app/actions.ts` の1箇所だけに置く | 取り込みスクリプトが `actions.ts` を通らない。**実データのほとんどが記録されない**（→ §5.2） |

## 7. 次にやること（この設計書の外）

管理画面を目的別に作り直す。今は1ページに登録フォーム6個と一覧4個が縦に並んでいて、目的から作業へたどれない。

**状態は Issue #110 で作った**（→ [状態画面の設計書](2026-08-15-110-admin-status-screen-design.md)）。この表の「過ぎた非アクティブ」の中身は、同 §3.1 が実測で決めている。

**銘柄とテーマ・イベント・貢献度は Issue #112 で作った**（→ [管理画面を分ける 設計書](2026-08-16-112-split-admin-screens-design.md)）。5画面はこれで揃った。「登録フォーム6個と一覧4個」は実測とずれており、着手時は登録5つ・一覧3つだった。

| 画面 | 出すもの |
|---|---|
| 状態 | 抜けを見つけて赤くする。登録されている銘柄で次の決算日が未登録・決算月なし・出典の表示名なし・過ぎた非アクティブ・休場日リストの不足 |
| 銘柄とテーマ | 登録と一覧。区切りを付けて並べる |
| イベント | 登録・貼り付け一括・一覧（**誰が入れたか**を出す） |
| 貢献度 | 入力者ごとの件数 |
| 監査ログ | 管理者だけ。新しい順。**絞り込みは作らない**（下記） |

**監査ログの画面は Issue #111 で作った。絞り込みも件数の上限も付けていない。** この表の「日付と種別で絞る」から変えた理由は3つある。

- 件数の上限は、§5.4 の復元（`WHERE a.id = <監査ログのID>`）を古い行から順に画面へ届かなくする。`previous_values` は消した行の唯一の写しなので、上限は戻す手段そのものを消す
- 全件をHTMLに出せばブラウザの検索が全件に効く。書くコードは0行で、上限やページ送りを付けるとその検索が表示中のぶんにしか届かなくなる
- 増える速さを測った。窓に追いついた状態で `pnpm import:stat` を叩くと監査ログは0件しか増えない（2ヶ月ぶん新しく入っても2件）。残りは3人の手入力だけ

苦しくなったら `action` での絞り込みを足す。画面が件数を出すので、増え方は見て分かる。

## 9. どこが仮定か

| 記述 | 依存している仮定 | 動いたら |
|---|---|---|
| 管理者のメールアドレスを設定に置く | 「管理者は1人で、めったに変わらない」 | 管理者が増減するたびに配信し直すのが重くなったら、役割をDBで持つ形に変える |
| 削除だけを管理者に限る | 「作成と編集は誰が間違えても直せる」 | 編集で取り返しのつかない上書きが起きたら、編集も分ける |
| 監査ログを見る画面を管理画面の刷新に回してよい | 「それまでは psql で読める」 | 管理者が psql を使わない運用になったら前倒す |
| IPアドレスとブラウザの種類を持たない | 「入力者は身内3人」 | 入力者を外部の人に広げたら要る |
