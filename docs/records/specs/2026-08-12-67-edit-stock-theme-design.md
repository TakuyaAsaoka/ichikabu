# 銘柄とテーマの編集・削除 設計書

- 対応 Issue: [#67 銘柄とテーマを管理UIから編集・削除できるようにする](https://github.com/TakuyaAsaoka/ichikabu/issues/67)
- 根拠: [イベントの編集・削除 設計書](2026-08-11-43-edit-event-design.md)（§3 画面構成・§4 共通部品・§9 やらないこと）、[管理UI設計書](2026-08-09-6-admin-ui-design.md)（§3 画面構成・§5 登録の失敗の扱い・§12 やらないこと）、[テーマ登録 設計書](2026-08-11-27-theme-registration-design.md)（§3.1 テーマ名の前後の空白）

## 1. 目的と結論

**登録済みの銘柄とテーマを画面から直せて、消せるようにする。** イベントは Issue #43／#47 で直せるようになったが、他の4テーブルは登録しかできず、打ち間違いを直す手段が `psql` しか無い。

| 項目 | 決定 |
|---|---|
| 削除の文言 | エラーコード `23001` のときだけ別の対応表を引く。参照元を名指しする（→ §2） |
| 編集の場所 | 別ページ `/stocks/[id]` `/themes/[id]`。一覧の各行に「編集」リンクを置く（→ §3） |
| 直せる範囲 | 銘柄の4列すべて（市場・ティッカー・銘柄名・決算月）とテーマ名（→ §4） |
| 一緒に消えるもの | テーマ所属の件数を確認ダイアログに出す（→ §4.1） |
| 空白だけの名前 | `trimmedName()` を1つ作り、銘柄名とテーマ名の登録・更新の4箇所から通す（→ §5） |
| IDの判定 | `isEventId` を `isId` に変え、3テーブルで1つにする（→ §6） |
| 保有・テーマ所属 | 今回はやらない。[Issue #68](https://github.com/TakuyaAsaoka/ichikabu/issues/68)（→ §9） |

判断が割れた5点は、立場を固定した2体の討論と開発用DBでの実測で決めた。決め手は §2・§3・§4・§5・§6 の各節に書く。

## 2. 削除で返る制約名は登録のときと同じ

**この Issue の核心。** `src/db/write.ts` の `MESSAGES` は制約名から画面に出す日本語を引く表で、外部キー違反に「その銘柄は無い」「そのテーマは無い」を割り当てている。参照されている行を削除すると**同じ制約名**が返るため、そのまま通すと「参照されていて消せない」行に「その銘柄は無い」と出る。意味が正反対になる。

開発用DBで実測した結果（取り引きの中で削除して戻した）。

| 操作 | コード | 制約名 |
|---|---|---|
| イベントから参照されている銘柄を消す | `23001` | `event_stock_id_stock_id_fk` |
| 保有から参照されている銘柄を消す | `23001` | `holding_stock_id_stock_id_fk` |
| イベントから参照されているテーマを消す | `23001` | `event_theme_id_theme_id_fk` |
| どこからも参照されていない銘柄を消す | — | 成功 |
| テーマを消したとき | — | 成功し、`theme_stock` が 1件 → 0件 |

### 2.1 コードで振り分ける

`23001` は `ON DELETE restrict` に阻まれたときの専用のコードで、外部キー違反の `23503` とは別物である。

**このコードが返る経路は削除だけである。** `restrict` が付いているのは `ON DELETE` の側だけで、外部キー8本の `ON UPDATE` はすべて `no action`（`drizzle/0000_simple_blacklash.sql` 104〜111行）。参照先の `stock.id` `theme.id` は `generatedAlwaysAsIdentity` で更新されない。実測でも、イベントから参照されている銘柄のティッカーは問題なく更新できた。

そのため `run()` の中で表を選ぶだけで足りる。呼び出し側は1箇所も変わらない。

```ts
const message = (code === RESTRICT_VIOLATION ? DELETE_MESSAGES : MESSAGES)[constraint ?? ""];
```

| 制約名 | 画面に出す文 |
|---|---|
| `event_stock_id_stock_id_fk` | その銘柄はイベントに使われていて消せない |
| `holding_stock_id_stock_id_fk` | その銘柄は保有に登録されていて消せない |
| `event_theme_id_theme_id_fk` | そのテーマはイベントに使われていて消せない |

`theme_stock` の外部キー2本は `ON DELETE cascade` のため、削除ではこの表に来ない。

### 2.2 1つの文にまとめない

「他のデータから使われているため消せない」の1文にする案は採らない。Issue #67 の Scenario 2 が「その銘柄は**イベントに**使われていて消せない」と参照元を名指ししている。1文にまとめると、運用者は消せない銘柄を前に `event` と `holding` のどちらを先に片づければよいか分からず、`psql` を叩くことになる。この Issue の目的そのものが消える。

**PostgreSQL は最初に当たった制約だけを返す。** イベントと保有の両方から参照されている銘柄では、イベントの文言が出て、イベントを消してもう一度押すと保有の文言が出る。2回踏むことになるが、これは1文にまとめても同じで、違うのは各回に次の一手が示されるかどうかだけ。

先に `COUNT` で数えて一度に全部出す案も採らない。管理UI設計書 §5 の「事前に存在確認せず、制約違反を日本語に訳す」に反する。

## 3. 画面構成

| パス | 中身 |
|---|---|
| `/` | 銘柄一覧とテーマ一覧の各行に「編集」リンクを足す |
| `/stocks/[id]` | 銘柄の編集フォームと削除ボタン |
| `/themes/[id]` | テーマの編集フォームと削除ボタン |

イベントの `/events/[id]` と同じ形にする。`StockForm` / `ThemeForm` に初期値と Server Action を渡し、登録と編集で同じフォームを使う（イベントの編集・削除 設計書 §4.2 と同じ）。

### 3.1 一覧の行で直す案を採らない理由

テーマは1列しかないため、一覧の行に入力欄を置けば新しいファイルは増えない。それでも別ページにする。

- **イベントの編集・削除 設計書 §3.2 が「削除は編集ページに置く。一覧に並べると誤って押しやすい」と決めている。** この決定は、確認ダイアログ（同 §4.1 の `ActionForm` の `confirm`）を定義したのと同じ文書・同じ回のものである。確認ダイアログがある上で「一覧に並べない」と決めており、「確認があるから一覧でよい」は成り立たない
- 一覧インラインにすると、同じ `app/page.tsx` の中に「リンクで別ページへ」（イベント）と「その場で直す」（銘柄・テーマ）の2つの流儀が並ぶ
- Issue #67 の「検証」が、あるべき姿の出力として `ls app | grep -c "^stocks$\|^themes$"` の結果を **2** と定めている

## 4. 銘柄の4列すべてを直せるようにする

市場とティッカーを読み取り専用にする案は採らない。

- 一意の制約は `(market, ticker)` に、外部キーは `stock.id` にかかっている。**実測のとおり、イベントから参照されている銘柄のティッカーを変えても参照は外れない**
- 更新で踏む制約の日本語は既に `MESSAGES` にある。`stock_market_ticker_unique`（その市場のティッカーは登録済み）も `stock_fiscal_month_market_check`（決算月はJP銘柄にだけ入れられる）も、更新のときにそのまま正しい意味になる。**足す文言は1つも無い**
- 読み取り専用にすると、打ち間違えた銘柄が「イベントから参照されていて消せない・直せない」で行き止まりになる

### 4.1 一緒に消えるものを知らせる

`theme_stock` の外部キーは銘柄側もテーマ側も `ON DELETE cascade` で、銘柄を消してもテーマを消してもテーマ所属が黙って消える。確認ダイアログに**件数**を入れる。

```
「半導体」を削除する。所属している銘柄2件も外れる。取り消せない。
```

名前は並べない。`window.confirm` は素のダイアログで、件数が多いと読まれない。**外れる相手の一覧は編集ページに出す**ので、名前はそちらで見る。

確認ダイアログは削除できるかどうかを知らない。参照が残っていれば OK を押しても何も起きないが、そのときは §2 の名指しの文言が出るため、運用者は何も消えていないと分かる。

### 4.2 保有に登録された銘柄は、この Issue の後も画面から消せない

**残る行き止まり。** 「その銘柄は保有に登録されていて消せない」は「先に保有を消せ」と指示しているが、**保有の削除は Issue #68 のため、画面にその手段が無い。** 保有に入っている銘柄を消すには、いまも `psql` で `holding` の行を消す必要がある。

イベントの側は同じことにならない。参照元のイベントは `/events/[id]` から消せる。行き止まりになるのは保有だけである。

先に Issue #68 をやればこの行き止まりは消える。順番を逆にした理由は、Issue #67 のほうが「列を持つ2つ」で作業が大きく、共通の部品（IDの判定・確認ダイアログ）がこちらに寄っているため。

> **この行き止まりは Issue #68 で解消した。** 保有一覧の各行から `/holdings/[stockId]` へ行き、保有を外せる。「その銘柄は保有に登録されていて消せない」が出たら、保有を外してから銘柄を消す。詳細は[保有とテーマ所属の削除 設計書](2026-08-12-68-delete-holding-theme-stock-design.md)。

## 5. 空白だけの名前

`stock.name` と `theme.name` は `notNull` だが空文字を弾く CHECK が無い。`<input required>` は `""` しか弾かず `"   "` を通すため、**空白だけの名前が入る**。実測でもテーマ名を `"   "` に更新できた。

前後の空白を落とす処理と、落とした結果が空なら弾く判定を1つの関数にまとめ、4箇所（`createStock` / `updateStock` / `createTheme` / `updateTheme`）から通す。

```ts
function trimmedName(value: string): string | null {
  const trimmed = value.trim();
  return trimmed === "" ? null : trimmed;
}
```

**`createStock` にも入れる。** 今の `createStock` は空白を落としていない。`updateStock` にだけ入れると、登録では通る `"   "` が更新では弾かれる食い違いが生まれる。同じ穴なので同じ関数でふさぐ。

CHECK 制約（`btrim(name) <> ''`）にする案は採らない。

- CHECK は空を弾けても、「半導体 」を「半導体」にそろえる正規化はできない。テーマ登録 設計書 §3.1 が挙げた「見分けの付かない選択肢が2つ並ぶ」問題は正規化でしか消えないため、CHECK はこの関数の置き換えにならず**追加**になる
- 管理UI設計書 §12 が「`stock.name` の空文字を弾く CHECK 制約の追加」をやらないことと定めている

`stock.ticker` には要らない。`stock_ticker_check`（`^[0-9A-Z.-]+$`）が空白も空文字も既に弾く。

## 6. IDの判定

`isEventId`（整数かつ 1〜2147483647）を `isId` に変えて1つにする。`event.id` `stock.id` `theme.id` はすべて `integer().primaryKey().generatedAlwaysAsIdentity()` で、判定に差が入る余地が無い。

文言だけは引数で分ける。「そのイベントは見つからない」を「そのデータは見つからない」に弱めると、既に画面に出ている情報が減る。

```ts
function invalidId(id: number, label: string): string | null {
  return isId(id) ? null : `その${label}は見つからない`;
}
```

## 7. テスト

`src/db/write.test.ts` に足す。

| テスト | 確かめること |
|---|---|
| 銘柄の4列すべてを更新するとDBの行が変わる | `updateStock` |
| 参照されている銘柄のティッカーを変えても参照は外れない | §4 の根拠を固定する |
| 既にある市場とティッカーの組に変えるとエラー文が返る | 更新でも `stock_market_ticker_unique` が効く |
| 決算月を残したままUS銘柄に変えるとエラー文が返る | 更新でも `stock_fiscal_month_market_check` が効く |
| イベント／保有から参照されている銘柄を消すとエラー文が返る | §2 の対応表。「その銘柄は無い」が出ないこと |
| 両方から参照されていると参照元を1つずつ知らせる | 2回に分けて消す挙動を固定する（→ §2.2） |
| テーマ所属は一緒に消える | `ON DELETE cascade`（→ §4.1） |
| イベントから参照されているテーマを消すとエラー文が返る | §2 の対応表 |
| 空白だけの名前は登録・更新ともエラー文が返る | §5 の4箇所 |
| 問い合わせに渡せないIDの更新・削除はエラー文が返る | §6 の `isId` |

## 8. 目視確認の手順

1. `pnpm dev` で起動し、サインインする
2. 銘柄一覧の「編集」を押し、`/stocks/[id]` に4列の値が入っていることを見る
3. 銘柄名を直して更新し、一覧・保有一覧・イベント一覧の表示が新しい名前になることを見る
4. その銘柄を対象にしたイベントを登録し、銘柄の削除を押して「その銘柄はイベントに使われていて消せない」が出ることと、銘柄が消えないことを見る
5. そのイベントを消してから銘柄を削除し、確認ダイアログが出ることと、OKで消えることを見る
6. テーマに銘柄を所属させ、テーマの削除の確認ダイアログに所属の件数が出ることを見る
7. テーマ名を空白だけにして更新し、「テーマ名を入れる」が出ることを見る
8. `/stocks/abc` と `/stocks/9999999999` が404になることを見る

## 9. やらないこと

| やらないこと | 理由 |
|---|---|
| 保有・テーマ所属の削除 | [Issue #68](https://github.com/TakuyaAsaoka/ichikabu/issues/68)。この2つは主キー以外の列が無く「削除だけ」になる。**保有に登録された銘柄が削除の行き止まりになったまま残る**（→ §4.2） |
| 消せるかを先に数えて確認ダイアログを出し分ける | 管理UI設計書 §5「事前に存在確認せず」に反する。確認と削除の間に別の登録が割り込む穴も戻る（→ §4.1） |
| 空文字を弾く CHECK 制約の追加 | 管理UI設計書 §12 のまま。正規化の代わりにならない（→ §5） |
| 一覧の並べ替え・絞り込み・ページ送り | 管理UI設計書 §3 のまま。件数が少ない |
| 更新の履歴を残す | 利用者=運用者=自分の1人（全体設計書 §12） |
| 更新・削除の `openapi.yaml` への追加 | Server Action で完結し、自作のパスではない（管理UI設計書 §12 と同じ理由） |
