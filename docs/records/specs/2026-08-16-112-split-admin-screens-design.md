# 管理画面を銘柄とテーマ・イベント・貢献度に分ける 設計書

対象 Issue: [#112](https://github.com/TakuyaAsaoka/ichikabu/issues/112)

[入力者を3人にする・監査ログ 設計書](2026-08-14-82-multi-editor-audit-design.md) §7 が「管理画面を目的別に作り直す」と決めた5画面のうち、残りの3枚を作る。状態は [#110](2026-08-15-110-admin-status-screen-design.md)、監査ログは #111 で作った。

## 1. 目的と結論

1ページに8つの区画（登録5つ・一覧3つ）が縦に並んでいて、やりたい作業にたどり着けない。目的ごとの画面に分ける。

| 項目 | 決定 |
|---|---|
| 銘柄とテーマ | `/`（`server/app/page.tsx`）。今の画面からイベントの3区画を抜いたもの |
| イベント | `/events`（`server/app/events/page.tsx`）。登録・貼り付けでまとめて登録・一覧（誰が入れたかを出す） |
| 貢献度 | `/contributions`（`server/app/contributions/page.tsx`）。入力者ごとの件数 |
| 画面の行き先 | `server/app/nav.tsx` の `Nav`。サインイン済みの画面が1行ずつ呼ぶ（→ §3） |
| 誰が入れたか | 監査ログから引く。3つの状態に分ける（→ §4） |
| 貢献度の数え方 | `audit_log` を対象で絞らず、入力者ごとに登録・更新・削除を数える（→ §5） |

区画は8→5、`app/page.tsx` は203行→133行になった。

## 2. `/` を銘柄とテーマにする

**`/` は実データの画面のまま残す。** 入口だけの画面も `redirect("/events")` の1行も作らない。

`/` を指している場所を数えた（2026-08-16 実測）。

| 場所 | 数 | 分ける後の行き先 |
|---|---|---|
| `app/actions.ts` の `redirect("/")` | 7 | 銘柄・テーマ・テーマ所属の5本はそのまま。イベントの2本（`editEvent`・`removeEvent`）だけ `/events` |
| `app/actions.ts` の `revalidatePath("/")` | 12 | そのまま（→ §7） |
| 画面の `href="/"`（「一覧に戻る」） | 6 | 全部消して `Nav` に置き換える（→ §3） |
| サインイン後の着地点 | 3 | そのまま（`app/signin/page.tsx`・`app/signin/signin-form.tsx` の2箇所） |
| 管理者ではない人の追い返し先 | 1 | そのまま（`app/audit/page.tsx`） |

`/` を転送にすると、この表の下3行がすべて「1回余分に飛ぶ」形になる。得られるのは URL の名前が中身と揃うことだけで、`/` に中身を残せば直すのは2本で済む。

## 3. 画面の行き先は `app/nav.tsx` に置く

**レイアウトには置かない。** 2枚とも置かない理由が別にある。

| 置き場所 | 置かない理由 |
|---|---|
| `app/layout.tsx` | `app/signin/page.tsx` も包むため、サインインしていない人の画面にリンクが並ぶ（状態画面 設計書 §4 が実測で棄却済み） |
| `app/(admin)/layout.tsx`（サインイン済みだけを包む2枚目） | **テストが届かない。** 画面のテストは `renderToStaticMarkup(await Page())` で描いており（`test/render-page.ts` の `render`）、レイアウトは Next.js のルーターが合成するためこの呼び方では一度も描かれない。監査ログのリンクを入力者に見せない判定（`isAdmin`）が、確かめられない場所へ移る |

状態画面 設計書 §4 は「#112 で戻る線が増えすぎたら2枚目の `layout.tsx` を足す」と予告していたが、**足さない形に変えた。** 予告は #111 が `renderToStaticMarkup(await Page())` でテストを書けると示す前のもの。1行ずつ呼ぶ形なら、画面のテストがそのまま `Nav` の判定を見られる（`app/events/page.test.ts` の2件）。

各画面が持っていた「一覧に戻る」6本は消す。`Nav` が5つの行き先を全部出すため重複する。

## 4. 誰が入れたかは3つの状態に分ける

材料は監査ログしか無い。`event` に作成者の列は作らない（監査ログ 設計書 §5.5）。

| 監査ログの状態 | 画面の出力 | 中身 |
|---|---|---|
| 記録があり `user_id` が入っている | 表示名 | 人が画面から入れた |
| 記録があり `user_id` が NULL | `取り込み` | 取り込みスクリプトが入れた |
| 記録が無い | `記録なし` | 監査ログより前に入った |

**下2つを混ぜない。** 混ぜると、取り込みスクリプトがやっていない登録を取り込みの手柄にする。`schema.ts` が `onDelete: "restrict"` を選んで避けたのと同じ嘘を、表示側で作ることになる。

3つ目が実在することは実測で確かめた。`audit_log` は `drizzle/0004_careful_calypso.sql` で足したもので、そのファイルに `INSERT` は0件（遡って埋める処理が無い）。`src/db/seed-event.ts` にも `record` の呼び出しが0件ある。

引き方は `src/db/audit.ts` の `creatorNamesByEventId`。1行ずつ問い合わせず、登録の記録を全件1回読んで `Map` にする。`event.id` は `generatedAlwaysAsIdentity` で消しても番号が回ってこないため、1イベントにつき登録の記録は最大1件になる。

## 5. 貢献度は対象で絞らない

`src/db/audit.ts` の `countByUser`。監査ログ 設計書 §5.5 が載せている問い合わせと同じ形で、入力者ごとに登録・更新・削除を数える。

**対象（銘柄・テーマ・イベント・テーマ所属）で絞らない。** 12の Server Action がすべて `app/actions.ts` の `audited` を通るので既に全部入っており、絞るとかえって条件が1つ増える。

削除の列は、管理者以外はいつも0になる（削除は `requireAdmin` を通る）。それでも出す。0が並ぶこと自体が「削除できるのは管理者だけ」を画面で表す。

並びは登録の多い順。同じ件数どうしの順序をSQLは決めないため、表示名まで並び順に入れる。

## 6. テストの検出力を壊して確かめた

新しいテストが本当に守っているかを、実装をわざと壊して確かめた（2026-08-16 実測）。

| 壊した箇所 | 赤くなったテスト |
|---|---|
| 「記録なし」を「取り込み」にまとめる | イベントの画面「記録の無いイベントは『記録なし』と出る」 |
| `Nav` の `isAdmin` を反転する | イベントの画面「入力者には監査ログへの行き先が出ない」「管理者には〜出る」 |
| `countByUser` の並び順を消す | 貢献度の画面「登録の多い入力者が先に出る」 |
| `redirect("/events")` を `/` に戻す | `app/actions.test.ts`「イベントを編集できて、イベントの画面へ戻る」「〜削除できて〜」 |

**最後の1件は、直す前は緑のまま通っていた。** `rejects.toThrow(/NEXT_REDIRECT/)` は行き先を1文字も見ていない（行き先は例外の `digest` にしか入っておらず、`message` は `NEXT_REDIRECT` だけ）。`test/render-page.ts` の `redirectedTo` で行き先を取り出す形に直した。

## 7. 棄却した案

| 案 | 棄却の理由 |
|---|---|
| `/` を入口だけの画面にする | 中身が `app/nav.tsx` と同じになる。ナビの2枚目の写しでしかない |
| `/` を `redirect("/events")` にする | §2 の表の下3行が全部1回余分に飛ぶ。`app/actions.ts` の `redirect` も7本すべて書き換えになる |
| サインイン済みだけを包む `app/(admin)/layout.tsx` を足す | ナビがテストで描かれない場所へ移る（→ §3）。7つの `page.tsx` の物理移動も要る |
| `revalidatePath("/")` 12本を新しいパスへ付け替える | `pnpm build` の出力で全ルートが `ƒ (Dynamic)`（server-rendered on demand）。消すキャッシュを持っていない。整理は別の話として残す |
| 貢献度をイベントの登録だけに絞る | `where` が1つ増えるぶんコードが長くなる。テーマ所属を100件貼った人が0件と出る |
| 誰が入れたかを1件ずつ問い合わせる | イベントの件数だけ問い合わせが出る。全件1回読んで `Map` で足りる |

## 8. どこが仮定か

- **貢献度の並びを登録の多い順にした。** 更新が多い人が下に来る。3人で使ってみて具合が悪ければ変える
- **貢献度を全員に見せている。** 監査ログ（前後の値まで出る）とは見えるものの重さが違うため管理者に限っていない
- **`Nav` は今いる画面を目立たせない。** 現在地を出すには `usePathname` が要り、ブラウザ側で動く部品になる。5つ並ぶだけの間は要らないと判断した
