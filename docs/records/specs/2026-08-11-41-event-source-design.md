# イベントの出典表示 設計書

- 対応 Issue: [#41 出典を画面に出し、内閣府・省庁の公表予定を使えるようにする](https://github.com/TakuyaAsaoka/ichikabu/issues/41)
- 根拠: [全体設計書](2026-08-02-1-ichikabu-design.md)（§4.2 列の判断・§5.1 出典ポリシー）、[イベント取得API設計書](2026-08-08-3-events-api-design.md)、[管理UI設計書](2026-08-09-6-admin-ui-design.md)（§5 登録の失敗の扱い）

## 1. 目的と結論

**イベントの日付をどこで確認したかを、利用者に見える形で出す。** これは全体設計書 §5.1「出典を増やすときの手順」のステップ2（条件を満たす手段を先に決める）にあたる。これができると、出典の記載を条件とする内閣府・省庁の公表予定を使えるようになる。

| 項目 | 決定 |
|---|---|
| 出典の持ち方 | `event.source_name` を足し、既存の `event.source_url` と対にする。両方入れるか両方空にするかを CHECK で強制（→ §3） |
| 文言の決め方 | `source_name` は自由入力。規約が求める書き方は運用者がそこに書く（→ §3.2） |
| API | `Event.source` を足す。`{ name, url }` か `null`（→ §4） |
| iOS | シートの行に、補足の下に出す。URLを開けるリンクにする（→ §5） |
| §5.1 の書き換え | 内閣府・省庁を「使う」に、日銀を「使わない」に（→ §6） |

## 2. 起票後に分かったこと

Issue #41 の起票時に日銀と内閣府の利用条件を読んだ。着手時にさらに総務省・財務省・e-Stat を読み、次が分かった。

| 出典 | 適用される規約 | 商用 | 出典の記載 |
|---|---|---|---|
| 内閣府・総務省・財務省 | 公共データ利用規約（第1.0版） | 可 | 条件 |
| e-Stat（サイト） | 政府標準利用規約（第2.0版） | 可 | 条件 |
| 日銀 | 独自 | **不可**（事前の相談が必要） | — |

府省ごとに規約が違うのではなく、同じ規約を各府省が採用している形だった。**府省ごとに判定し直す必要はない。**

## 3. 出典の持ち方

### 3.1 名前とURLを対にする

`event.source_url` は既にある（全体設計書 §4.2）が、URLだけでは「出典：内閣府」にならない。公共データ利用規約の記載例は府省名を含む。

```
出典：「○○動向調査」（D庁）（当該ページのURL）、PDL1.0
```

そこで `event.source_name`（NULL可のテキスト）を足す。

**名前があるならURLも要る。逆は許す。**

```sql
CHECK (source_name IS NULL OR source_url IS NOT NULL)
```

名前だけあってURLが無いと、画面に出した出典から元のページへたどれない。URLだけの状態は許す。`source_url` は「この日付をどこで確認したか」の記録で、用途は権利の照会と誤登録の追跡、どちらも**運用者が見る**ものだからである（全体設計書 §4.2）。出典の記載が条件でない出典（各社IR）では、記録は残すが画面には出さない、という使い方になる。

判定はDBに置く（管理UI設計書 §5）。

**当初は「両方入れるか両方空にするか」（`num_nonnulls(...) <> 1`）で設計したが、これは誤りだった。** 既に登録済みの決算イベント3件が `source_url` だけを持っており、マイグレーションが制約違反で止まった。実装中に実際に流して分かったもので、本番でも同じことが起きる形だった。

### 3.2 文言は運用者が書く

`source_name` に何を書くかはアプリで決めない。規約が求めるものは出典ごとに違い、これから増える。

| 規約が求めるもの | `source_name` の書き方の例 |
|---|---|
| 出典の記載 | `内閣府` |
| 規約名の記載（記載例に含まれる） | `内閣府（PDL1.0）` |
| 編集・加工した旨とその主体 | `内閣府（PDL1.0）を加工して作成` |

**「編集・加工にあたるか」をアプリ側で決めない。** 公表予定の日付を、こちらで付けた名称でイベントとして登録する行為が加工にあたるかは、出典と登録内容による。自由入力にして運用者が判断する。仕組みで縛ると、判断が変わるたびにコードを直すことになる。

### 3.3 却下した案

| 案 | 却下の理由 |
|---|---|
| `source_url` だけを使い、URLのドメインを画面に出す | `www.cao.go.jp` は「内閣府」ではない。規約の記載例と形が違う |
| 出典のテーブルを作り、イベントから参照する | 出典は当面数件で、名前の重複を防ぐ必要も出ていない。テーブルを1つ増やすほうが重い |
| 名前とURLを1つの列に文字列で入れる | URLだけをリンクにできない。画面で切り出すには結局分ける必要がある |

## 4. API

`openapi.yaml` の `Event` に `source` を足す。

```yaml
source:
  type:
    - object
    - "null"
  required: [name, url]
  properties:
    name: { type: string }
    url: { type: string, format: uri }
```

**2つの平たい項目（`sourceName` と `sourceUrl`）にしない。** 平たいと「両方あるか両方無いか」が型で表せず、DBのCHECKで守っている関係が契約側で崩れる。オブジェクトなら `null` か「名前とURLが揃ったもの」の2通りしか表せない。

計算で作る権利日のイベント（`rights-<銘柄ID>-<年>`）は出典を持たない。休場日カレンダーからこちらで計算した日付で、転記元が無いため。`source` は `null` になる。

## 5. iOS

シートの行（`CalendarView.swift` の `row(for:)`）の、補足の下に出す。

```
★★★ 9月CPI  10:30
消費者物価指数（2026年8月分）
総務省が公表する全国の消費者物価指数
出典: 総務省（PDL1.0）        ← 足す。タップで元のページを開く
```

カレンダーのセルには出さない。セルは1日2件までで略号しか入らない（全体設計書 §10.2）。

`source` が `null` の行には何も出さない。行の高さが変わるだけで、出典が無いことの説明は要らない。

## 6. §5.1 の書き換え

出典表の可否を2行書き換える。

| 出典 | 今 | 変更後 | 理由 |
|---|---|---|---|
| 内閣府・省庁 | 今は使わない | **使う** | 出典を出す手段ができた |
| 日銀 | 今は使わない | **使わない** | 商用目的が対象外で、出典を出しても解けない |

**FRB は触らない。** 条件が未確認のままで、§5.1 は「1つずつ増やす」と決めている。

## 7.1 実際に動かして確かめたこと

管理UIからDBを経てiOSの画面に出るまでを、通しで確認した。

| 経路 | 確かめ方 | 結果 |
|---|---|---|
| 管理UI → DB | 画面から公表予定を1件登録し `psql` で行を見た | `source_name` と `source_url` が入る |
| DB → API | `curl /api/events` | `source: {name, url}` が返る。出典なしの行と権利日は `null` |
| API → iOS の読み取り | `IchikabuTests/APIClientTests.swift` | 出典つきのJSONから名前とURLを読める |
| iOS の描画 | シミュレータで2026年9月18日のセルを開いた | シートに `出典: 総務省（PDL1.0）` がリンクで出る |

```
9月18日（金）
★★★ CPI  08:30:00
消費者物価指数（2026年8月分）
出典: 総務省（PDL1.0）
```

シミュレータで画面を出す手順は [iOS の画面を目視で確認する](../../guides/ios-visual-check.md) に書いた。ウィンドウが開かない・クリックが効かない・座標がずれる、の3つで詰まったため、同じところで止まらないように残してある。

## 8. やらないこと

| やらないこと | 理由 |
|---|---|
| 出典の自動取得 | 全体設計書 §2 で「やらないこと」。着手時に e-Stat の API を確かめたが、公表予定日を返す機能が無く、予定は各府省のサイトに分散していた（→ §9） |
| FRB を「使う」にする | 条件が未確認。1つずつ増やす（§5.1） |
| 出典ごとの規約名を選択肢にする | 出典が数件のうちは自由入力で足りる |
| ~~管理UIの一覧に出典を出す~~ | ~~一覧は登録できたかの確認に使うもので、出典は確認に要らない（管理UI設計書 §3）~~ **Issue #43 で取り消した。** 出典の表示名を入れ忘れた行は規約の条件を満たさない行なので、入っているかどうかの確認そのものが必要になった（→[イベントの編集・削除 設計書](2026-08-11-43-edit-event-design.md) §3.1） |

## 9. 自動化について（この Issue の範囲外の記録）

着手時に e-Stat の API を調べた結果を残す。**公表予定日は API で取れない。**

| 調べたこと | 結果 |
|---|---|
| e-Stat API の提供機能 | 統計表情報・メタ情報・統計データ（数値）など7つ。公表予定日を返す機能は無い |
| 公表予定がまとまった機械で読める形（CSV等） | 見つからなかった。公表予定は各府省のサイトのページにある |

自動化するならページから取ることになり、全体設計書 §2 が「やらないこと」に入れているスクレイピングにあたる。自動化の可否は別Issueで判断する。
