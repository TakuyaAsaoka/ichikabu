# 保有とテーマ所属の削除 設計書

- 対応 Issue: [#68 保有とテーマ所属を管理UIから削除できるようにする](https://github.com/TakuyaAsaoka/ichikabu/issues/68)
- 根拠: [銘柄とテーマの編集・削除 設計書](2026-08-12-67-edit-stock-theme-design.md)（§2 削除の文言・§3.1 一覧の行で直す案・§4.1 一緒に消えるもの・§4.2 保有の行き止まり）、[イベントの編集・削除 設計書](2026-08-11-43-edit-event-design.md)（§3.2 削除の置き場所・§4.1 `ActionForm`・§6 IDの判定）、[管理UI設計書](2026-08-09-6-admin-ui-design.md)（§3 画面構成）

## 1. 目的と結論

**登録済みの保有とテーマ所属を画面から消せるようにする。** `holding` と `theme_stock` は主キー以外の列を持たないため、直す対象が無く「削除だけ」になる。間違えたら消して入れ直す。

| 項目 | 決定 |
|---|---|
| 削除の場所 | 別ページ `/holdings/[stockId]` `/themes/[id]/stocks/[stockId]`（→ §2） |
| 確認ダイアログ | **出さない**（→ §3） |
| 保有の利用者 | セッションから取る。URLにもフォームにも出さない（→ §2.1） |
| IDの判定 | 既存の `isId` をそのまま使う。複合主キーなので2列とも判定する（→ §4） |
| 削除の条件 | 主キーの2列とも `where` に入れる（→ §4.1） |

判断が割れた2点（削除の場所・確認ダイアログ）は、立場を固定した2体の討論と、この worktree での実測で決めた。

## 2. 削除は別ページに置く

`/stocks/[id]` `/themes/[id]` `/events/[id]` と同じ形にそろえる。

| パス | 中身 |
|---|---|
| `/holdings/[stockId]` | 対象の銘柄1行と「この保有を外す」ボタン |
| `/themes/[id]/stocks/[stockId]` | テーマ名・対象の銘柄1行と「この所属を外す」ボタン |

一覧の各行に削除ボタンを置く案は採らない。

- **イベントの編集・削除 設計書 §3.2 が「削除は編集ページに置く。一覧に並べると誤って押しやすい」と決めている。** この2つに編集ページは無いが、理由の文が述べているのは一覧の性質であって、列の有無ではない。行き先が無いなら行き先を作る
- **銘柄とテーマの編集・削除 設計書 §3.1 が、まさに「新しいファイルが増えないケース」について一覧インラインを棄却している。** 「テーマは1列しかないため一覧の行に入力欄を置けば新しいファイルは増えない。それでも別ページにする」。同 §3.1 は「確認ダイアログがある上で『一覧に並べない』と決めており、『確認があるから一覧でよい』は成り立たない」とも書いた。**この設計書は確認ダイアログを出さないと決めた（→ §3）ので、一覧インラインにすると誤爆を止めるものが1つも無くなる**
- **操作の回数は変わらない。** 別ページなら「リンク → ボタン」の2回、一覧インライン＋確認ダイアログなら「ボタン → OK」の2回
- 一覧インラインにすると、同じ `app/page.tsx` の中に「リンクで別ページへ」（銘柄・テーマ・イベント）と「その場で削除」（保有・所属）の2つの流儀が並ぶ

### 2.1 URLに出すのはデータ由来の列だけ

`holding` の主キーは `(user_id, stock_id)`。**`user_id` はURLにもフォームにも出さない。** 管理UI設計書 §3 のとおりセッションから取る。URLに出すと、他人のIDを打てば他人の保有ページが開く形になる。

`theme_stock` の主キーは `(theme_id, stock_id)` でどちらもデータなので、両方URLに出す。

`app/themes/[id]` の下にぶら下げるため、**テーマIDのスラッグ名は既存の `[id]` に合わせる。** `[themeId]` に変えても Next.js 16.3.0 ではビルドが通る（実測）が、同じ位置で `/themes/[id]` と名前が割れる。

捨てた案。

| 案 | 捨てた理由 |
|---|---|
| `/holdings/[userId]/[stockId]` | 利用者IDをURLに出すことになる（→ §2.1） |
| `/theme-stocks/[themeId]-[stockId]` | 1つの文字列に2つの値を詰めて自前で分解することになる。`isId` に渡す前に分解が挟まり、イベントの編集・削除 設計書 §6 が塞いだ穴を別の形で作り直す |
| `/stocks/[id]` に相乗り | 同じページに「全員に効く銘柄の削除」と「サインイン中の利用者にだけ効く保有の削除」が並ぶ |

## 3. 確認ダイアログは出さない

`ActionForm` の `confirm` を渡さない。既にある3つ（銘柄・テーマ・イベント）とは違う扱いにする。

- **運ぶ情報が1つも無い。** 既存の3つは「取り消せない」か、一緒に消える件数を運んでいる（銘柄とテーマの編集・削除 設計書 §4.1）。`holding` と `theme_stock` を参照するテーブルは1つも無く（実測: `grep -c "=> holding\.\|=> themeStock\." src/db/schema.ts` → `0`）、巻き添えは0件。主キー以外の列も無いので、消えて失われる情報が無い
- **入れ直しが `<select>` 1回で済む。** `app/page.tsx` の `HoldingForm` と `ThemeStockForm` で元に戻る。イベントの編集・削除 設計書 §3.2 が確認を挟んだ理由「消したイベントは戻せない」が当たらない
- 中身の無い確認を足すと、**情報を運んでいる残り3つの確認まで反射で OK されるようになる**
- 誤爆を止める役目は、別ページへ移動するという明示の操作が担う。両方は買わない

## 4. IDの判定

`isId`（`src/db/write.ts`）をそのまま使う。`stock.id` `theme.id` はどちらも `integer().primaryKey().generatedAlwaysAsIdentity()` で、判定に差が入る余地が無い。

複合主キーなので**2列とも判定する**。`deleteThemeStock` はテーマIDを先に判定し、次に銘柄IDを判定する。

`user_id` は `text` 列でセッションから来るため判定しない。数への変換を通らないので、型変換エラーで 500 になる経路が無い。

### 4.1 主キーの2列とも `where` に入れる

`deleteHolding` は `user_id` と `stock_id` の両方を条件にする。銘柄IDだけで消すと**他の利用者の保有まで消える**。`deleteThemeStock` も同じで、銘柄IDだけで消すと他のテーマの所属まで消える。

利用者は当面1人（全体設計書 §12）だが、`createHolding` が最初から `user_id` をセッションから受け取る形にしたのと同じ理由で、削除も最初から2列で絞る。

## 5. 外部キー違反は起きない

`holding` と `theme_stock` を参照しているテーブルは1つも無い（→ §3 の実測）。**`DELETE_MESSAGES` に足す文言は1つも無い。** 銘柄・テーマの削除が `restrict` に弾かれる問題（銘柄とテーマの編集・削除 設計書 §2）は、この2つには起きない。

逆向き（この2つが他を参照する側）は削除に関わらない。

| 参照 | `ON DELETE` |
|---|---|
| `holding.user_id` → `user.id` | `cascade` |
| `holding.stock_id` → `stock.id` | `restrict` |
| `theme_stock.theme_id` → `theme.id` | `cascade` |
| `theme_stock.stock_id` → `stock.id` | `cascade` |

## 6. テスト

`src/db/write.test.ts` に足す。

| テスト | 確かめること |
|---|---|
| 保有を消しても銘柄は消えない | Issue #68 Scenario 1 |
| 他の利用者の保有は消えない | §4.1。`user_id` を `where` から落とすと赤くなる |
| 所属を消してもテーマも銘柄も消えない | Issue #68 Scenario 2 |
| 他のテーマの同じ銘柄の所属は消えない | §4.1。`theme_id` を `where` から落とすと赤くなる |
| 存在しない組の削除は何も起きない | 0件削除を成功として返す |
| 問い合わせに渡せないIDの削除はエラー文が返る | §4 の `isId`。500 にならないこと |

`where` の条件を片方だけに落として実際に赤くなることを確かめた（「他の利用者の保有は消えない」「他のテーマの同じ銘柄の所属は消えない」の2件が落ちる）。

画面の2ページに自動テストは足さない。`/stocks/[id]` `/themes/[id]` `/events/[id]` も持っておらず、§7 の目視確認でそろえる。

## 7. 目視確認の手順

1. `pnpm dev` で起動し、サインインする
2. 銘柄を登録し、保有に登録する。保有一覧の「削除」から `/holdings/[stockId]` へ行き、銘柄名が出ることを見る
3. 「この保有を外す」を押し、確認ダイアログが出ずに一覧へ戻ること、保有一覧から消えて銘柄一覧には残っていることを見る
4. テーマを登録し、所属を登録する。テーマ一覧の所属の行の「削除」から `/themes/[id]/stocks/[stockId]` へ行き、テーマ名と銘柄名が出ることを見る
5. 「この所属を外す」を押し、所属だけが消えてテーマも銘柄も残ることを見る
6. `/holdings/abc` `/holdings/9999999999` `/themes/1/stocks/abc` が404になることを見る
7. 保有に入っている銘柄を `/stocks/[id]` から消そうとして「その銘柄は保有に登録されていて消せない」が出ること、保有を外してから消せることを見る（銘柄とテーマの編集・削除 設計書 §4.2 の行き止まりの解消）

## 8. やらないこと

| やらないこと | 理由 |
|---|---|
| `/stocks/[id]` から `/holdings/[stockId]` へのリンク | Issue #68 の受け入れ条件に無い。保有一覧から消せるようになれば行き止まりは解けている |
| テーマ編集ページの所属一覧から外せるようにする | `/themes/[id]` の所属一覧は「テーマを消すと何が一緒に外れるか」を出すもの（銘柄とテーマの編集・削除 設計書 §4.1）で、所属を管理する一覧ではない |
| 保有の「編集」 | 主キー以外の列が無く、直す対象が存在しない |
| 一覧の並べ替え・絞り込み・ページ送り | 管理UI設計書 §3 のまま |
| `openapi.yaml` への追加 | Server Action で完結する（管理UI設計書 §12 と同じ理由） |
