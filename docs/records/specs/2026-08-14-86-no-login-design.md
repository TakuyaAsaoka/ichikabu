# iOS のログインを廃止する 設計書

対象 Issue: [#86](https://github.com/TakuyaAsaoka/ichikabu/issues/86)（イベントに対象を持たせ、銘柄一覧APIを足す）・[#87](https://github.com/TakuyaAsaoka/ichikabu/issues/87)（iOS で持ち株を選び、端末に保存して絞り込む）・[#88](https://github.com/TakuyaAsaoka/ichikabu/issues/88)（iOS のログインを廃止する）

## 1. 目的と結論

**iOS アプリのログインを廃止する。** 持ち株は端末に持ち、イベントの絞り込みも端末で行う。サーバーは誰が見ているかを知らなくなる。**管理UI（イベントを入力する画面）のログインは Google のまま残す。**

きっかけは「入力者を3人にしたとき、他人のパスワードを管理者が決めて設定ファイルに平文で書くことになる」という問題だった。調べた結果、**そのパスワードは iOS のログインのためだけに存在していた**（管理UIは既に Google）。ログインそのものを無くせば、パスワードという資産ごと消える。

App Store Review Guidelines 5.1.1(ii) も同じ方向を指している。

> If your app doesn't include significant account-based features, let people use it without a login.

### 3段階に分ける

各段階の終わりで品質ゲートが通る形にする。

| 段階 | Issue | やること | 終わりの状態 |
|---|---|---|---|
| 1 | #86 | 契約を広げる | `Event` に対象を足し、`GET /api/stocks` を新設。**既存の動作は変わらない** |
| 2 | #87 | iOS で持ち株を選んで絞る | 選ぶ画面＋端末保存＋絞り込み。サーバーはまだ保有で絞っているので、端末の絞りは**さらに狭めるだけ** |
| 3 | #88 | 認証を外す | 認証と保有の絞りを消す。**端末の絞りだけが残る** |

**先に認証を外してはならない。** 絞り込みが1つも無い状態になり、全員に全銘柄のイベントが出る。

## 2. なぜ「iOS も Google サインイン」ではないのか

パスワードを消すだけなら、iOS のサインインを Google に差し替えるほうが小さい（サーバー側は変更なし。`socialProviders.google` は既にある）。それでもログイン廃止を選ぶ理由は次の3つ。

| # | 理由 |
|---|---|
| 1 | **ログインを残しても、将来の分析機能（§14 #12「似た持ち株のユーザーが買っている銘柄」）の材料は1件も貯まらない。** サインアップが無効で（§9）、利用者は `pnpm db:seed` でしか作れない。他人のデータが入る経路が無い。**将来のために残すログインが、将来の材料を産まない** |
| 2 | §14 #12 に着手する日には、サインアップ・アカウント削除（5.1.1(v)）・パスワード再設定・メール送信をまとめて作ることになる。今のログインはその下地ではなく、**その作業で捨てられる側** |
| 3 | 5.1.1(ii) の論点が消える。公開のときに必ず通る道 |

**引き換えに失うもの**: サーバーが持ち株を知らなくなる。§4.2 が `holding.created_at` を「将来の集合知機能の原料そのもの」として持つと決めていたが、上の理由1のとおり**今のままでも原料は貯まっていない**。

## 3. 段階1: 契約を広げる（#86）

### 3.1 `Event` に対象を足す

今の `Event` は `kind`（`market` / `theme` / `stock`）しか持たず、**どの銘柄・どのテーマかを示すIDが無い**（変更前の `deriveKind` がIDを捨てていた）。これでは端末で絞れない。

条件は「端末側で『この銘柄を持っている人に出すイベントか』を判定できること」。市場イベントは `GLOBAL` が全員向け、`JP` / `US` は保有銘柄の市場で判定するため、市場の情報も要る。

**採った形**: `kind` はそのまま残し、`target` を1つ足す。`target` は `type` で場合分けする3つの形（`{type:"market", market}` / `{type:"theme", themeId}` / `{type:"stock", stockId}`）のどれか1つになる。

| 判断 | 根拠 | 棄却した案 |
|---|---|---|
| `target` を3つの形の場合分けにする | 銘柄のIDが `GET /api/stocks` では整数、`GET /api/events` では文字列という状態を作らない。同じものが経路によって別の型になると、端末は比べるたびに変換を書くことになる | `target: string`（`kind` で読み方が決まる文字列） |
| `kind` を残す | 色分けが `kind` で書かれている（`ios/Ichikabu/EventLayout.swift`）。消すと `Event` 自体を場合分けの形にすることになり、共通の欄9つを取り出す手書きが約45行増える | `kind` を消して `target` に統合する |

**`kind` と `target.type` は同じ区分を2回書く形になる。** 契約はこの2つが食い違う組み合わせも表せてしまう（全体設計書 §5 が「種別を宣言する列も作らない」とした理由と同じ弱点）。消す形は上の表のとおり代償が大きいので、次の2つで塞ぐ。

- サーバーは種別と対象を1つの関数（`deriveKindAndTarget`）から同時に返す。出どころを1つにする
- `route.test.ts` に、3種別それぞれで `kind` と `target.type` が一致することを見るテストを1件置く

**市場だけは、端末で変換が残る。** `Stock.market`（`JP` / `US`）と `EventMarket`（`JP` / `US` / `GLOBAL`）は値の集合が違うため、契約でも生成後の型でも別の型になる。段階2で「保有銘柄の市場と市場イベントの市場が一致するか」を比べるときは文字列に直す。**変換を書く場所は1箇所に閉じる。** 契約では両方を名前付きにして、片方に市場を足すときにもう片方も見えるようにした。

**イベント取得API設計書の決定を2つ覆している。** 記録しておく。

| 覆した決定 | 位置 | なぜ覆したか |
|---|---|---|
| 対象の識別子は返さない | イベント取得API設計書 §3 | 当時の根拠は「iOS が使う用途は色分けだけ」。iOS が自分で絞るようになり、用途ができた |
| 最後の `stock` は else 扱いにする | 同 §4 | `target` は分岐の中で `stock_id` の値そのものを使うため、else では取れない |

**ありえない行（対象の3列がどれも埋まっていない行）は返さない。** DBの CHECK 制約 `num_nonnulls(market, theme_id, stock_id) = 1` が禁じているが、型からは見えない。イベント取得API設計書 §4 が「例外は投げない」と決めているため、`null` にして `filter` で落とす。同じファイルの `rightsEvents` は空配列で落としており、落とし方は違うが、例外を投げない点は同じ。**§4 のこの決定は覆していない。**

### 3.2 `GET /api/stocks` を新設する

持ち株を選ぶには銘柄の一覧が要る。市場・ティッカー・銘柄名に加えて、**所属テーマのID（`themeIds`）を返す**。

**テーマ所属を段階1で渡す理由。** 全体設計書 §5 は「1つの出来事は必ず1行で登録する。行の複製は禁止」と決めており、銘柄とテーマの両方に効かせたい出来事は**テーマイベント1行**にすると指示している（§5.0.1 の「2銘柄に効く1つの出来事」も専用テーマを作れとしている）。つまり銘柄の出来事がテーマイベントとして登録されるのは規則の側の話で、例外ではない。端末に所属が無いと、テーマイベントは「全員に出す」か「誰にも出さない」しか選べず、どちらも §5 の表（そのテーマの銘柄を持つ人）と違う。段階3でサーバー側のテーマ判定が消えたあと、絞る場所は端末以外に残らない。

**テーマの名前は返さない。** テーマを画面に出す要件が #86 にも #87 にも無い。名前が要る日に `GET /api/themes` を足せばよく、そのとき `themeIds` はそのまま残せる。

**決算月は返さない。** 権利日はサーバーが計算して `Event` として返すため、端末に使い道が無い（§5.2）。

**認証は付けない。** 返すのは運用者が登録した銘柄だけで、誰が何を持っているかは含まない。付けると #87 で持ち株の画面にトークンを配る配線が要り、#88 でその配線を外す往復になる。

**この段階では認証も絞り込みも変えない。** 既存のテスト13件は、応答の形を丸ごと固定している2件に `target` を足すだけで通る（iOS も、応答の例を書いた2件に足すだけ）。

**管理UIが持っていた市場の一覧も消した。** `server/src/db/schema.ts` の `EVENT_MARKETS` を使う。市場を1つ足したとき、契約とDBは型が拾うのに、管理UIの `<select>` だけが黙って取り残される状態だった。

## 4. 段階2: iOS で持ち株を選んで絞る（#87）

### 4.1 保存先は `UserDefaults`

置くのは選んだ銘柄IDの配列だけ。数十バイトで、スキーマもマイグレーションも要らない。

設計書 §12 は「SwiftData / オフラインキャッシュ」を「数KBのデータに永続化層は過剰」として外している。**矛盾しない。** §12 が過剰だと言っているのは**イベントを端末に持つキャッシュの層**で、ここで置くのは選んだ銘柄IDだけである。イベントは今までどおり起動時に取り直す。

### 4.2 iCloud への差し替えは Apple Developer Program 加入後

`NSUbiquitousKeyValueStore`（アプリごとに1MB、利用者の iCloud 容量を消費しない）に変えると、機種変更で引き継がれる。書き方は `UserDefaults` とほぼ同じ。

**使うには Apple Developer Program（年 US$99）への加入が要る**（Xcode の iCloud の capability を有効にするため）。加入は先の予定なので（§14 #2）、まず `UserDefaults` で作る。

**読み書きを1つの型に閉じる。** 差し替えるときにその型の中だけを変えれば済む形にする。抽象化の層は作らない（実装が1つしかない差し替え口は §12 の考え方に反する）。

### 4.3 機種変更で消えることをどう見るか

| 見方 | 中身 |
|---|---|
| 消えるのは銘柄IDの配列だけ | §2・§4 のとおり `holding` は株数も取得単価も持たない。選び直しは数タップ |
| **今のログインでも同じ問題は解決していない** | `ios/Ichikabu/TokenStore.swift:25` が `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` を指定しており、**機種変更でトークンは必ず消えて再ログインになる**（実測で確認） |
| 今のほうが復旧しにくい | 再ログインに要るパスワードは管理者が決めたもので、本人が変える画面も再設定のメールも無い。しかも iOS に持ち株の画面が無いため、持ち株が変わったら管理UIを持つ人に頼むしかない |

**段階2はここを改善する。** 利用者が自分で持ち株を選べるようになる。

## 5. 段階3: 認証を外す（#88）

### 5.1 消すもの

| 場所 | 中身 |
|---|---|
| `server/app/api/events/route.ts` | 認証の判定と保有・テーマ・市場の絞り込み（約56行）。`where` は `active` の1条件だけになる |
| `openapi.yaml` | `security` / `bearerAuth` / `"401"`（5箇所） |
| `ios/Ichikabu/SignInView.swift`・`TokenStore.swift`・`ios/IchikabuTests/TokenStoreTests.swift` | ファイルごと（計106行） |
| `ios/Ichikabu/APIClient.swift` | `signIn`・トークンの取り出し・認証のエラー |
| `ios/Ichikabu/IchikabuApp.swift` | サインイン画面との出し分け |
| `server/src/db/schema.ts` ほか | `holding` テーブルと、関連する書き込み・画面・テスト |

### 5.2 `server/src/rights.ts` は変えない

`rightsDates(year, fiscalMonth)` は年と決算月だけを受け取る純関数で、認証にも保有にも依存していない。変わるのは `route.ts` の問い合わせ1本だけ。

```
今:   .from(stock).innerJoin(holding, …).where(and(eq(holding.userId, userId), isNotNull(stock.fiscalMonth)))
後:   .from(stock).where(isNotNull(stock.fiscalMonth))
```

**休場日リストをサーバーに置く判断（§14 #7）はそのまま残る。** #7 の決め手は2つあり、①「計算の材料が server にある」は弱まるが、②「iOS に置くと更新のたびに App Store 審査が要り、更新が止まると翌年の権利日が出せなくなる」は変わらない。②だけで server 計算を支える。

### 5.3 管理UIへの波及

`holding` を消すと、管理UIから保有の登録が消える。**「グリーンの判定」（決算日が未登録の銘柄を赤くする）の対象が、保有銘柄から『登録されている全銘柄』に変わる。** 判定としてはむしろ素直になる。

### 5.4 副産物

応答が全員同じになるので、CDN に載せられる（`Cache-Control`）。今は利用者ごとに違うのでキャッシュできない。利用者が増えてから決めてよい。

## 6. データ量

実測（2026-08-14、開発DB）: 有効なイベント39件で 8.9KB。

1銘柄あたり年7件（決算4件＋権利日3年ぶん）として見積もると次のようになる。市場イベントは銘柄数に関係しない。

| 銘柄数 | 件数 | 生のJSON |
|---|---|---|
| 3（今） | 58 | 約20 KB |
| 30 | 247 | 約86 KB |
| 100 | 737 | 約256 KB |

起動時の1回だけの取得で、銘柄100件でも256KB。**手入力で到達する規模ではない。**

**先に効いてくるのは銘柄数ではなく年数のほう。** `route.ts` には今も日付での絞り込みが無く、過去のイベントも全件返している（認証の有無と無関係な既存の性質）。カレンダーの表示範囲は起動月の前後12ヶ月（§10）なので、切る位置は決まっている。効いてきたら1行足す。

## 7. 棄却した案

| 案 | 棄却の理由 |
|---|---|
| iOS も Google サインインにする（ログインは残す） | パスワードは消えるが、§2 の理由1〜3 が残る。**今のログインは将来の資産にならない** |
| 設定ファイルからパスワードを消す運用にする | 緩和にとどまる。管理者がパスワードを決めることは変わらない |
| 端末の識別子でサーバーに持ち株を持つ | 実質アカウントなのに認証が無い（識別子を知られれば他人の持ち株を読める）。端末を変えると別人になる。App Privacy で識別子の収集を申告することになる。**匿名の識別子では「同じ人」の保証が無く、将来の集合知機能にも使えない** |
| 持ち株を SwiftData で持つ | 過剰。§12 に反する |
| 段階を分けず一度に変える | 認証を先に外すと絞り込みが1つも無い状態になる |

## 9. どこが仮定か

| 記述 | 依存している仮定 | 動いたら |
|---|---|---|
| 全イベントを返してよい | 「銘柄数は手入力で増える範囲にとどまる」 | 自動取り込みで銘柄が数百を超えたら、日付か対象で絞る |
| 持ち株を端末に置いてよい | 「消えても選び直せる」（株数も取得単価も持たないため） | §14 #11 で株数を持つようになったら、消えると痛い。そのときはサーバー同期を作る |
| ログインが要らない | 「利用者ごとに違うのはイベントの絞り込みだけ」 | §14 #12（似た持ち株の人の銘柄）に着手したら覆る。**そのPRでサインアップと一緒に作る** |
| `UserDefaults` で足りる | 「機種変更の引き継ぎは後回しでよい」 | Apple Developer Program に加入したら `NSUbiquitousKeyValueStore` に差し替える |
