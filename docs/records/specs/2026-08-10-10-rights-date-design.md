# 権利確定日・配当落ち日の計算 設計書

- 対応 Issue: [#10 権利確定日・配当落ち日の計算](https://github.com/TakuyaAsaoka/ichikabu/issues/10)
- 根拠: [全体設計書](2026-08-02-1-ichikabu-design.md)（§4.1 休場日はテーブルにしない・§4.2 権利確定日は保存せず計算する・§14 #7）、[イベント取得API設計書](2026-08-08-3-events-api-design.md)

## 1. 目的と結論

**`stock.fiscal_month` と休場日リストから権利付最終日を計算し、`GET /api/events` の返り値に混ぜてカレンダーに出す。**

全体設計書 §4.2 は「権利確定日・配当落ち日は保存せず、決算月と営業日カレンダーから計算で出す」と決めているが、**誰が計算するかが未定義**のまま残っていた（§14 #7）。この設計書でそれを決める。

| 項目 | 決定 |
|---|---|
| 計算の実行主体（§14 #7） | **server**（→ §2） |
| 休場日リストの置き場所 | `server/src/rights.ts` に日付の配列（→ §4） |
| リストの範囲 | 2025・2026・2027年。**リストに無い年は計算しない**（→ §4） |
| 契約の変更 | `Event.id` を integer → **string**（→ §5） |
| カレンダーに出す件数 | 1銘柄あたり年1件（権利付最終日）。配当落ち日は `note` に書く（→ §6） |
| 中間配当 | **扱わない**（→ §8） |

## 2. 未決事項 #7 の決着 — server で計算する

| 論点 | server | iOS |
|---|---|---|
| 計算に要る材料（保有銘柄と `fiscal_month`） | **すでに手元にある**（`/api/events` が保有で絞り込んでいる） | 届いていない。**保有一覧APIの新設が要る** |
| 休場日リストの年1回更新 | **デプロイで差し替わる** | アプリ更新なので App Store 審査を通す必要がある。更新が止まると翌年の権利日が出せなくなる |
| サーバー往復なしで年をまたげるか | またげない | またげる |
| テスト | Vitest | XCTest |

**3つ目の「往復なしで年をまたげる」は、この画面では利点にならない。** カレンダーの表示範囲は起動月の前後12ヶ月に固定されており（`CalendarView.swift`、Issue #8 設計書 §2 判断5）、その範囲のイベントは起動時の1回の取得で出揃うため、そもそも往復が発生しない。

残る2点はどちらも server に有利で、とくに休場日の更新が App Store 審査に縛られる点は、放置すると**毎年1回かならず効いてくる**。よって server で計算する。

**代償**: 計算したイベントには DB の行IDが無いため、契約の `id` を文字列にする必要がある（→ §5）。

## 3. 計算の定義

| 用語 | 定義 |
|---|---|
| 営業日 | 土曜・日曜でなく、休場日リストにも無い日 |
| 権利確定日 | 決算月の**月末営業日**。月末日が営業日でなければ遡って直近の営業日 |
| 権利付最終日 | 権利確定日の**2営業日前** |
| 配当落ち日 | 権利確定日の**1営業日前**（＝権利付最終日の翌営業日） |

「2営業日前」は日本市場の決済が 2019年7月から T+2（約定日の2営業日後に受け渡し）になったことによる。権利確定日に株主名簿へ載るには、その日までに受け渡しが済んでいる必要がある。

**月末日そのものではなく月末営業日を基準にする。** 会社が定款で定める基準日は「3月31日」のような暦日だが、名簿の書き換えは営業日にしか行われないため、実務上の権利確定日は月末営業日になる。2024年3月末（3/31 が日曜）の権利付最終日が各社の公表値で 3月27日になっているのは、権利確定日が 3/29（金）だからである。3/31 を基準にすると 3/28 になり、公表値と合わない。

## 4. 休場日リスト

`server/src/rights.ts` に `YYYY-MM-DD` の文字列の配列として置く。テーブルにしない理由は全体設計書 §4.1 のとおり（年1回更新すれば足りるリストにDBは過剰）。

**土曜・日曜は載せない。** 曜日は計算で分かるので、リストに入れるのは「平日なのに取引所が閉まる日」だけにする。中身は国民の祝日・振替休日・国民の休日に、年末年始の休場（12月31日・1月1日・1月2日・1月3日）を加えたもの。

**範囲は 2025・2026・2027年の3年。** カレンダーの表示範囲が起動月の前後12ヶ月なので、暦年では最大3年ぶんあれば足りる。

**リストに無い年は計算しない。** 祝日は法律で決まり、春分・秋分の日は前年2月の官報で確定する。まだ確定していない年を推測で埋めると、間違った日付を「計算結果」として出すことになる。出さない方を採る。

**リストは年1回更新する。** 更新の手段は作らない（全体設計書 §14 の運用節に1行足す）。更新を忘れると、リストの最終年を過ぎた時点で権利日が静かに出なくなる。

## 5. 契約の変更 — `Event.id` を string にする

計算で作るイベントは DB の行ではないので、`event.id`（識別列の整数）を持てない。`openapi.yaml` の `Event.id` を `integer` から `string` に変える。

| イベント | `id` |
|---|---|
| DBに登録したもの | `"12"`（行IDを文字列にしただけ） |
| 計算で作ったもの | `"rights-3-2026"`（`rights-<stock.id>-<年>`） |

**負の整数を計算イベントに割り振る案は採らない。** 「負なら計算」という規則がどこにも書かれないまま暗黙の前提になり、後から見て読めない。文字列なら値そのものが由来を説明する。

**iOS 側の変更は実質ない。** `id` は `ForEach(events, id: \.id)` の識別にしか使っておらず、`String` も `Int` も同じように使える（`APIClientTests.swift` のテスト用JSONだけ直す）。

### 並び順

`openapi.yaml` は「`startDate`・`time`・`id` の昇順に並ぶ」と書いており、いまは SQL の `ORDER BY` がそれを満たしている。計算イベントを混ぜると SQL だけでは並べきれないので、**結合したあとに server 側で1回並べ替える**。SQL の `ORDER BY` は外す（二重に並べる意味がない）。

並び順の規則は次のとおりで、`openapi.yaml` の記述もこれに合わせる。

1. `startDate` の昇順
2. `time` の昇順。`null`（時刻なし）は後ろ
3. `id` の文字列としての昇順

`time` の `null` を後ろにするのは、いまの SQL（PostgreSQL の `ORDER BY` は昇順で `NULL` が最後）の挙動をそのまま保つため。

## 6. 生成するイベントの中身

対象は「保有している JP 銘柄のうち `fiscal_month` が入っているもの」×「休場日リストが載っている各年」。1組につき1件を作る。

| 項目 | 値 | 理由 |
|---|---|---|
| `kind` | `stock` | 銘柄に紐づく出来事。カレンダーの色（琥珀）も既存のまま |
| `title` | `トヨタ自動車 権利付最終日` | シートに出す見出し |
| `shortLabel` | `7203権利` | seed の `7203決算` に揃えた形。幅8（半角4＋全角2）で、管理UIの上限10に収まる |
| `startDate` | 権利付最終日 | |
| `endDate`・`time` | `null` | 単日・時刻なし |
| `importance` | `2` | ★3にしない。毎年かならず来る予定を★3にすると、月サマリの「★3が N件」が毎年3月に膨らみ、「今月は荒れるか」の答えとして役に立たなくなる |
| `note` | `権利確定日 3月31日 ・ 配当落ち日 3月30日` | |

**カレンダーに出るのは権利付最終日の1件だけにする。** 配当落ち日を別の1件として出すと、保有銘柄の数だけ件数が倍になる。開発用の seed は3銘柄すべてが3月決算なので、分けた場合は3月の2日間がどちらも「2件＋ +1」になり、セルの枠を権利日で埋めてしまう。

配当落ち日は権利付最終日の翌営業日なので、片方が分かればもう片方も決まる。**独立した情報ではないため、独立した1件にしない。** 実際の日付はシートの `note` に書く。

引き換えに失うもの: 「今日が配当落ち日」がカレンダーのセルだけでは分からない。前日のセルをタップして `note` を読む必要がある。

## 7. ファイル構成

| ファイル | 変更 |
|---|---|
| `openapi.yaml` | `Event.id` を string に。並び順の記述を §5 に合わせる |
| `server/src/rights.ts` | **新規**。休場日リストと計算関数。DBに依存しない純関数だけを置く |
| `server/src/rights.test.ts` | **新規**。→ §9 |
| `server/app/api/events/route.ts` | 保有 JP 銘柄の取得を1本足し、計算イベントを結合して並べ替える。`ORDER BY` を外す |
| `server/app/api/events/route.test.ts` | `id` が文字列になったこと・計算イベントが混ざることを足す |
| `ios/IchikabuTests/APIClientTests.swift` | テスト用JSONの `id` を文字列にする |
| 全体設計書 §14 | #7 を解決済みにする。運用節に休場日リストの年1回更新を足す |

**計算を `route.ts` に直接書かない。** 権利日の計算は日付の規則だけで閉じており、認証もDBも要らない。別ファイルの純関数にすれば Vitest からDBなしで呼べて、§9 のテストが素直に書ける。

## 8. 扱わないもの

| 項目 | 理由 |
|---|---|
| 中間配当の権利日 | 中間配当を払うかどうかは銘柄ごとに違い、`fiscal_month` からは分からない。払わない会社に権利日を出すのは誤りになる。持たせるなら `stock` に列が要るので、必要になった時点で別に決める |
| US銘柄 | `fiscal_month` は JP のみ、休場日リストも JP のみ（全体設計書 §4.1）。未決事項 #8 のまま |
| 休場日リストの更新手段 | 年1回の書き換えに仕組みは要らない |
| 権利日を `event` テーブルに保存すること | 全体設計書 §4.2 で却下済み |

## 9. テスト

`server/src/rights.test.ts`（DB不要）。

| ケース | 期待する結果 |
|---|---|
| 2026年3月決算（月末 3/31 が営業日の火曜） | 権利確定日 3/31、権利付最終日 3/27、配当落ち日 3/30 |
| 2025年3月決算（証券会社の公表値と突き合わせる） | 権利確定日 3/31、権利付最終日 3/27、配当落ち日 3/28 |
| 2025年12月決算（12/31 が休場で月末営業日がずれる） | 権利確定日 12/30、権利付最終日 12/26、配当落ち日 12/29 |
| 2025年4月決算（**遡る途中に 4/29 の祝日が挟まる**） | 権利確定日 4/30、権利付最終日 4/25、配当落ち日 4/28 |
| 2026年1月決算（月末 1/31 が土曜） | 権利確定日 1/30、権利付最終日 1/28、配当落ち日 1/29 |
| 休場日リストに無い年（2030年） | 計算しない |

`server/app/api/events/route.test.ts` に1件足す: 3月決算の JP 銘柄を保有していると、権利付最終日のイベントが返る。

**上の4ケース目が要になる。** 土日だけを見て「2営業日前」を数えると 4/28 になり、祝日を数に入れて初めて 4/25 になる。休場日リストが計算に効いていることは、このケースでしか固定できない。
